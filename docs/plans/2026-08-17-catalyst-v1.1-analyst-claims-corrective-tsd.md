# Catalyst V1.1 Phase 4 Technical Specification

**Status:** Design specification
**Scope:** Evidence Analyst, corrective research, claim planning, Writer, and structural assurance
**Depends on:** Frozen V1.1 design, Phase 2 data contracts, Phase 3 agent-foundation contracts
**Out of scope:** Production implementation, Phase 5 transport/UI work, frontend behavior, and SSE protocol design

## 1. Executive Technical Assessment

The current semantic path cannot be incrementally relabeled into the V1.1 architecture. `Critic`, `Judge`, `Validator`, and `Finalizer` duplicate semantic decisions, permit later nodes to invent or rewrite causal claims, and blur epistemic insufficiency with technical failure. The safe migration is a controlled responsibility split:

1. one Evidence Analyst model call makes bounded evidence judgments and proposes at most three competing hypotheses;
2. deterministic normalization owns identities, recoverability, corrective-action construction, and the status ceiling;
3. one optional corrective retrieval round reuses the Phase 3 retrieval executor;
4. deterministic ClaimPlan construction and validation define the complete public fact/claim surface;
5. one streaming Writer call expresses only the validated plan; and
6. deterministic assurance either accepts the completed output or fails the run without rewriting it.

This satisfies the Frozen call budget: two normal-path model calls (`EvidenceAnalyst`, `Writer`) and three calls when one corrective round is executed (`EvidenceAnalyst` round 1, `EvidenceAnalyst` round 2, `Writer`). A single technical retry is allowed per model role only for transport, timeout, or invalid structured-schema output; it is never a semantic retry.

## 3. Current Semantic Runtime

The current graph is:

`context_builder → miner → critic → decision_router → (judge | expand_macro → miner | insufficient | system_error) → validator → finalizer`

| Current node | LLM call | Current responsibility | Actual promoted output | Downstream consumer | Frozen V1.1 equivalent |
|---|---:|---|---|---|---|
| `context_builder` | No | Build ticker/date/move context artifact | `context_artifact`, SHA-256, guards/cutoffs, phase | Miner/router | Phase 3 observation/task/context pipeline |
| `miner` | No | Retrieve, rerank, and expose Arm-B evidence | `retrieved_chunks`, `reranked_chunks`, retrieval metadata/cutoff, `arm_b_evidence`, degradation/error fields | Critic | Phase 3 `ResearchExecutor` + `EvidenceState` |
| `critic` | Yes | Grade chunks, reason about sufficiency, choose next action | `graded_evidence`, `all_graded_chunks`, `critic_reasoning`, `CriticDecision`, raw response/cost, phase or system error | Router, then Judge | `EvidenceAnalyst` plus deterministic normalizer |
| `decision_router` | No | Apply guards and route Critic decision | `router_edge`, `router_reason`, phase | Judge, expansion, insufficient, or system error | `AssessmentRouter` |
| `expand_macro` | No | Append macro terms, increment expansion/layer state, loop | Mutated `query`, `expansions_used`, `current_layer` | Miner | Typed corrective action and batch |
| `judge` | Yes | Create hypotheses/evidence links and final prose | `hypothesis_drafts`, projected `causes`, `summary_md`, `grounding_rate`, Judge-visible evidence/hash, raw response/cost | Validator | Split across Analyst, ClaimPlan, Writer, assurance |
| `validator` | Optional Yes | Enrich/check hypotheses and optionally request repair | `hypotheses`, projected `causes`, possibly rewritten `summary_md`, status, violations, attempts/repair count, support flags/cutoff | Finalizer | Deterministic `ClaimValidator` |
| `finalizer` | No | Rank hypotheses and recompute/fallback result status | `ranked_hypotheses`, `output_status`, phase | Runtime output | Thin terminal persistence only |

The current nominal path uses two model calls, but the second model call both decides causes and writes the answer. The optional Validator repair can add a third semantic call outside the Frozen budget. `expand_macro` is nominally routable but is not emitted by the current Critic decision builder.

## 6. Critic → Evidence Analyst

`Critic` becomes `EvidenceAnalyst`. The new node evaluates the complete, immutable `EvidenceAnalystContextPack` and returns one strict `AnalystDecision`. It does not receive mutable graph state, tool handles, backend details, retry history, internal budgets, or prior hidden reasoning.

The Analyst may:

- classify each visible evidence item as support, contradiction, weak context, lead-only, or irrelevant;
- propose up to three competing hypotheses using the Frozen cause taxonomy;
- identify material conflicts;
- propose missing evidence and bounded corrective intent;
- recommend `READY`, `FOLLOW_UP`, or `ABSTAIN`; and
- recommend a result status and attribution type that deterministic logic may only preserve or lower.

The Analyst does not assign runtime IDs, execute retrieval, calculate recoverability, choose backends, calculate the status ceiling, produce final prose, or repair its own semantic judgment through another call.

## 7. Analyst Prompt Contract

| Prompt receives | Prompt asks the model to do | Prompt must not expose or request |
|---|---|---|
| Hard constraints, MoveProfile/Observation, and session alignment | Compare bounded causal hypotheses | Database paths, providers, or tool names |
| Evidence items with stable IDs, source role, time, and bounded payloads | Bind every judgment to visible evidence IDs | Runtime-generated hypothesis/action/gap IDs |
| CoverageSummary, deterministic conflict signals, degradation, and explicit data/capability gaps | Distinguish weak evidence from missing evidence | Status-ceiling formula or threshold gaming |
| Research history, prior action fingerprints, and round-2 delta evidence IDs | Avoid duplicate requests and reassess cumulative evidence | Executable searches or permission to run them |
| Allowed cause, disposition, gap, and decision enums | Return exactly the strict schema | Free-form chain of thought |
| Round number and prior normalized assessment for round 2 | Revise, reject, promote, or retain hypotheses | Hidden prior response text or repair hints |
| Fixed policy statement and output limits | Surface contradictions and uncertainty | Retrieval commands, SQL, URLs, tickers, dates, or source filters |

The prompt requires concise, evidence-bound notes rather than hidden reasoning. It explicitly states that evidence may support one hypothesis and contradict another, that unknown-lineage reporting cannot establish independent corroboration, and that absence of evidence is not evidence of `NO_MATERIAL` unless the supplied coverage gates are satisfied.

## 8. CandidateHypothesis

The model emits a raw candidate keyed by a local reference. Deterministic normalization assigns the runtime ID.

The only allowed `CauseType` values are:

- `COMPANY_SPECIFIC_CATALYST`
- `CONTINUATION`
- `SECTOR_MOVE`
- `MACRO_EVENT`
- `FUNDAMENTAL_REPRICING`
- `REPORTING_OR_ANALYST_CONTINUATION`

`NO_MATERIAL_PUBLIC_CATALYST` is an attribution type, not a hypothesis cause. `MARKET_STRUCTURE_UNSUPPORTED` is a gap reason, not a cause. Neither may appear in `CandidateHypothesis.cause_type`.

| Field | Type/constraint | Owner | Round behavior |
|---|---|---|---|
| `hypothesis_ref` | Unique bounded local token such as `h1` | Model | Stable only within one response |
| `cause_type` | One of the six Frozen V1.1 cause classes | Model | May change in round 2 |
| `statement` | Bounded causal statement | Model | May be revised only from visible evidence |
| `mechanism` | Optional bounded mechanism | Model | Cannot be invented later by Writer |
| `supporting_evidence_ids` | Unique visible evidence IDs | Model | Revalidated each round |
| `contradicting_evidence_ids` | Unique visible evidence IDs | Model | Revalidated each round |
| `magnitude_fit` | `STRONG`, `PLAUSIBLE`, `WEAK`, `UNKNOWN` | Model | May change in round 2 |
| `proposed_role` | `PRIMARY`, `SECONDARY`, `CONTEXT`, `REJECTED` | Model | Subject to deterministic downgrade |
| `unresolved_gap_refs` | Local missing-evidence proposal refs | Model | Must resolve within the response |
| `hypothesis_id` | `hyp:<run>:<round>:<hash-prefix>` | Normalizer | Never model-generated |

At most three raw candidates are accepted. A candidate with no accepted semantic support cannot become a public primary or secondary causal claim.

## 9. EvidenceDecision

Each visible evidence item may have one decision:

| Field | Contract |
|---|---|
| `evidence_id` | Must resolve to the current ContextPack and EvidenceState |
| `disposition` | `SUPPORT`, `CONTRADICT`, `WEAK`, `LEAD_ONLY`, or `IRRELEVANT` |
| `supports_hypothesis_refs` | Zero or more valid local hypothesis refs |
| `contradicts_hypothesis_refs` | Zero or more valid local hypothesis refs |
| `reason_code` | Bounded documented enum, not prose reasoning |
| `note` | Optional short factual note with a strict length limit |

One evidence item may support `h1` while contradicting `h2`. It may not both support and contradict the same hypothesis. Ambiguous same-pair linkage is rejected during normalization, recorded as a semantic violation, and cannot be silently chosen in either direction.

## 10. AnalystDecision

| Field | Presence/constraint | Ownership | Round 1 | Round 2 |
|---|---|---|---|---|
| `schema_version` | Required scalar | Contract-selected/model-emitted | Required | Required, same supported version |
| `evidence_decisions` | Required list, may be empty | Model-owned | Complete over material judgments | Re-evaluates cumulative merged pack |
| `candidate_hypotheses` | Required list, 0–3 | Model-owned | Competing causal candidates | May revise/replace prior candidates |
| `conflicts` | Required list, may be empty | Model-owned | Material/non-material semantic conflicts | Must revisit unresolved material conflicts |
| `proposed_missing_evidence` | Required list, may be empty | Model-owned | Bounded proposals | Diagnostic only; no further retrieval |
| `research_decision` | Required enum | Model-owned | `READY`, `FOLLOW_UP`, `ABSTAIN` | Same enum, but `FOLLOW_UP` cannot execute |
| `recommended_status` | Required enum | Model-owned recommendation | `SUFFICIENT`, `PARTIAL`, `ABSTAIN` | Re-evaluated subject to ceiling |
| `proposed_attribution_type` | Required enum | Model-owned recommendation | `EVIDENCE_BACKED_CAUSAL` or `NO_MATERIAL_PUBLIC_CATALYST` | Re-evaluated subject to gates |

## 11. Cross-Field Invariants

| Invariant violation | Classification | Outcome |
|---|---|---|
| Unknown/extra field, invalid enum, duplicate local ref, more than three hypotheses | Structural schema | One technical schema retry, then `MODEL_SCHEMA_FAILURE` |
| Unknown evidence ID or hypothesis reference | Structural reference | One technical schema retry, then `MODEL_SCHEMA_FAILURE` |
| Multiple incompatible `PRIMARY` proposals | Structural response | One technical schema retry, then failure |
| Same evidence/hypothesis pair marked support and contradiction | Semantic normalization | Remove ambiguous relation, record violation, lower result if needed |
| `FOLLOW_UP` without missing-evidence proposal or linked intent | Semantic normalization | Do not retrieve; normalize to `READY` with final status ≤ `PARTIAL` and diagnostic `READY_WITH_PARTIAL`, or to `ABSTAIN` |
| Intent points to an unknown proposal | Semantic normalization | Drop intent and record violation |
| Proposed need has no available backend | Capability normalization | Mark gap non-recoverable; do not retry model |
| All proposed gaps are non-recoverable | Semantic normalization | No batch; `READY_WITH_PARTIAL` diagnostic or `ABSTAIN` |
| `READY` without an accepted supported hypothesis | Semantic normalization | Normalize to `ABSTAIN` |
| `ABSTAIN` with recommended `SUFFICIENT` | Semantic normalization | Preserve `ABSTAIN`; status cannot be sufficient |
| `NO_MATERIAL` with recommended `SUFFICIENT` | Semantic normalization | Cap at `PARTIAL`, or abstain if gates fail |
| Round 2 returns `FOLLOW_UP` | Round-exhaustion normalization | No third call; normalize to `READY` or `ABSTAIN` |

Structural retry exists to obtain a parseable contract, not to persuade the model toward a different conclusion.
`READY_WITH_PARTIAL` is a normalization diagnostic, not a fourth `ResearchDecision`; the normalized workflow value remains `READY`.

## 12. Structured Output / Retry

The canonical schemas use frozen Pydantic models with `extra="forbid"`, strict enums, bounded strings, bounded lists, and explicit schema versions. Provider adapters declare structured-output capability. Where supported, the Analyst uses `llm.with_structured_output(AnalystDecision, method="json_schema")`; otherwise it uses a JSON-only prompt and a strict parser over the same schema.

The current regex salvage, list coercion, unknown-category normalization, and partial-object recovery are removed. They obscure contract failures and make replay provider-dependent.

Retry policy:

- maximum two total attempts for an Analyst call;
- retry only transport failure, timeout, or invalid structured/schema/reference output;
- use the identical ContextPack hash, evidence set, and semantic instructions;
- a schema-repair suffix may restate formatting errors but cannot add/remove evidence or ask for reconsideration;
- never retry a valid semantic `ABSTAIN`, weak assessment, unsupported backend, or failed status gate; and
- after the retry is exhausted, fail the run as `MODEL_SCHEMA_FAILURE` or the applicable technical error.

## 13. AnalystDecision → EvidenceAssessment Normalization

`AssessmentNormalizer` is deterministic and produces an immutable `EvidenceAssessment`:

```text
validate runtime, pack, evidence, cutoff, and snapshot identities
strictly validate response references and assign deterministic hypothesis IDs
normalize evidence dispositions and hypothesis bindings
normalize conflicts and reject ambiguous same-pair relationships
validate missing-evidence proposals against reason mappings and capability registry
assign deterministic gap IDs and calculate recoverability
sanitize corrective hints and construct at most one eligible action/batch
calculate deterministic status ceiling
normalize READY / FOLLOW_UP / ABSTAIN under ceiling and round limits
hash and persist the complete assessment plus bounded violation codes
```

`EvidenceAssessment` contains the parsed `AnalystDecision`, normalized candidate hypotheses, normalized evidence decisions, normalized conflicts, typed gaps, optional corrective batch, normalized research decision, status ceiling, normalized status/type recommendations, violation codes, input hashes, policy versions, and assessment hash. It does not contain hidden chain of thought.

## 14. Status Ceiling

The Analyst supplies semantic support; deterministic code filters that support using EvidenceState materiality, eligibility, source role, lineage, conflict, temporality, and coverage.

| Condition | Maximum result |
|---|---|
| No accepted hypothesis or no semantically `SUPPORT`-linked material item | `ABSTAIN` |
| Defeating conflict on proposed primary hypothesis | `ABSTAIN` |
| Unresolved material conflict | `PARTIAL` |
| `NO_MATERIAL` attribution | `PARTIAL` |
| Commentary-only or unknown-role support | `PARTIAL` |
| One known independent reported-news group without primary-grade support | `PARTIAL` |
| At least one eligible `PRIMARY_AUTHORITY` or `DIRECT_PRIMARY` support item | May permit `SUFFICIENT` |
| At least two known independent reported-news groups | May permit `SUFFICIENT` |

`SUFFICIENT` additionally requires `STRONG` or `PLAUSIBLE` magnitude fit, no unresolved material contradiction, valid context prerequisites, and valid citations. Unknown-lineage news never counts toward independent corroboration. The normalized status is the lower of the model recommendation and the deterministic ceiling; the model may be more conservative, never less.

Integrity errors are not a low ceiling. They fail the run.

## 15. NO_MATERIAL Normalization

`NO_MATERIAL` is a bounded negative finding, not a default fallback. It requires all of the following:

**Deterministic coverage gates**

- company-primary sanity research completed;
- company-news sanity research completed;
- no required task or backend degraded;
- local textual-source coverage is adequate for the session window; and
- required market, sector, and peer context is available under policy.

**Analyst semantic gate**

- no accepted material-supported public catalyst is identified.

If both sets pass, `NO_MATERIAL` is permitted with a maximum status of `PARTIAL`. If deterministic gates fail, the result is `ABSTAIN` with explicit data/capability gaps, and the Writer must not state that no material catalyst exists.

The currently promoted snapshot does not contain production-grade benchmark/sector ETF context, so it cannot currently satisfy the full bounded `NO_MATERIAL` finding for policies that require that context.

## 16. MissingEvidence

The Analyst proposes missing evidence; code creates typed gaps and determines recoverability.

| Reason code | Proposer | Code validation | Recoverable now? / dependency | Execution or fallback |
|---|---|---|---|---|
| `MISSING_PRIMARY_CONFIRMATION` | Analyst | Need=`COMPANY_PRIMARY`; bounded session/prior/lookback scope; related candidate exists | Yes where the canonical primary corpus/backend is healthy; Phase 2 identity/eligibility | Existing facade via Phase 3 executor; otherwise non-recoverable gap |
| `MISSING_INDEPENDENT_CORROBORATION` | Analyst | Need=`COMPANY_NEWS`; accepted candidate lacks known-lineage corroboration | Yes where eligible news backend and lineage are healthy; Phase 2 independence | Existing facade via Phase 3 executor; unknown-lineage results do not satisfy it |
| `MISSING_PRIOR_SESSION_CONTEXT` | Analyst | Need=`COMPANY_PRIMARY` or `COMPANY_NEWS`; scope=`PRIOR_SESSION` | Yes only if prior-session query policy is supported; Phase 2 time/session identity | Canonical prior-session retrieval; otherwise explicit data/capability gap |
| `MISSING_SECTOR_CONTEXT` | Analyst or deterministic coverage projection | Need=`SECTOR_NEWS`; sector mapping must resolve from trusted asset metadata | Not in the promoted production path; Phase 2/3 sector mapping/corpus dependency | No action until capability exists; downgrade/abstain |
| `MISSING_MACRO_CONTEXT` | Analyst or deterministic coverage projection | Need=`MACRO_EVENT` or `MACRO_SERIES`; scope compatible with move/session | Series data exists but adapter wiring is pending; event text is capability-thin | Structured-series adapter when registered; event text otherwise non-recoverable |
| `MISSING_FUNDAMENTAL_CONTEXT` | Analyst or deterministic coverage projection | Need=`FUNDAMENTALS`; issuer and point-in-time scope code-owned | Data exists but adapter wiring is pending; Phase 2 stable fact IDs | Structured-fact adapter when registered; otherwise non-recoverable |
| `CONFLICT_REQUIRES_RESOLUTION` | Analyst | Must reference an existing `MATERIAL` conflict and a matching source dimension | Only if that dimension has a healthy backend and round remains | Execute matching typed need; otherwise preserve conflict and cap status |
| `MARKET_STRUCTURE_UNSUPPORTED` | Analyst or deterministic capability projection | Need must equal `MARKET_STRUCTURE` | No; explicitly unsupported in V1.1 | Never create action; limitation plus downgrade/abstain |
| `LOCAL_COVERAGE_GAP` | Analyst or deterministic coverage projection | Must name one explicit supported local need; vague “more research” is invalid | Conditional on the named need/backend | Execute only mapped need; otherwise non-recoverable gap |

The model proposal contains `proposal_ref`, `evidence_need`, `time_scope`, optional bounded `lookback_sessions`, bounded `expected_information`, `reason_code`, and optional related hypothesis/conflict refs. The normalizer assigns `gap_id`, capability state, recoverability, and policy metadata.

## 17. Corrective Intent / Action

`CorrectiveIntent` contains only a valid `proposal_ref` and up to three bounded query hints. Code owns all executable fields.

Action construction requires a valid recoverable gap, a compatible backend, remaining round budget, sufficient deadline, and no previous equivalent action fingerprint. Query hints are Unicode-normalized, whitespace-normalized, length-bounded, and stripped of URLs, SQL/tool syntax, source selectors, explicit ticker/date controls, and retrieval operators. They may carry only issuer/event concepts; ticker, cutoff, source filters, result limits, and windows come from trusted runtime context.

`action_id` is a deterministic hash over run, round, and canonical action inputs. `action_fingerprint` covers evidence need, time scope, lookback, trusted ticker scope, source filters, normalized hints, retrieval policy version, and time window. Repeated fingerprints are denied.

Source-class mapping is fixed by evidence need: `COMPANY_PRIMARY` selects eligible direct-primary/primary-authority classes; `COMPANY_NEWS` and `SECTOR_NEWS` select eligible reported-news classes; `MACRO_EVENT` selects configured macro-event sources; and structured needs select typed fact stores rather than textual source classes. The runtime enforces the original ticker/cutoff and cannot widen them from model text.

Result count, byte/token ingestion limit, and per-action timeout come from versioned runtime policy and are clamped to the remaining batch budget. The action stores requested and effective limits. Timeout or backend error produces a typed task result; it does not cause query mutation or a second corrective action.

## 18. expand_macro Migration

The current `expand_macro` node appends query text and loops to `miner`; it has no typed gap, capability check, stable fingerprint, or evidence-novelty stop condition. It is removed rather than generalized.

Macro correction becomes one variant of the common corrective contract:

- `MISSING_MACRO_CONTEXT` proposes `MACRO_EVENT` or `MACRO_SERIES`;
- capability registry decides whether a backend is available;
- trusted code builds a structured action;
- the Phase 3 retrieval executor runs the action;
- evidence merges through canonical identity and deduplication; and
- round 2 receives a rebuilt CoverageSummary and ContextPack.

No macro-specific graph loop or query-string mutation remains.

## 19. CorrectiveResearchBatch

V1.1 production policy permits `max_corrective_rounds=1` and `max_actions_per_batch=1`. A batch cannot be empty.

The batch contains a deterministic `batch_id`, run/round identity, `actions[]` containing exactly one action in production, action fingerprints, `shared_deadline`, monotonic internal deadline, `total_result_budget`, policy version, and cancellation token reference. The model supplies none of these values. The UTC deadline is persisted for audit; elapsed-time enforcement uses the monotonic deadline.

Batch creation is refused after any prior corrective batch, for a repeated fingerprint, with no executable recoverable gap, when the backend is unavailable, when budget/deadline is exhausted, or when cancellation is already requested. An empty batch is always invalid. `total_result_budget` is the minimum of versioned policy maximum and remaining run budget; the sole action receives no more than that total. Execution records per-action success, empty, degraded, failed, timed-out, or cancelled status plus returned canonical IDs. Cancellation is propagated into the retrieval/structured backend and prevents round-2 start until the executor reaches a terminal cancellation result.

Current capability posture:

| Need | Current/required backend posture |
|---|---|
| Company primary/news | Existing retrieval facade, migrated to Phase 3 executor |
| Sector news | Blocked until canonical sector mapping and eligible corpus are wired |
| Macro series | Data exists; structured retrieval adapter must be wired |
| Macro event text | Capability-thin; non-recoverable unless eligible source is configured |
| Fundamentals | Data exists; structured retrieval adapter must be wired |
| Market structure | Unsupported in V1.1 |

Execution results preserve per-task status, degradation, evidence IDs, canonical units, timing, cancellation, and error codes. Retrieval failure is not converted into analyst disagreement.

## 20. Stop Conditions

Corrective execution stops when any condition holds:

- round budget exhausted;
- action fingerprint already attempted;
- no valid recoverable gap;
- backend unavailable or degraded;
- deadline or result budget exhausted;
- cancellation requested;
- action returns no new canonical evidence unit; or
- round 2 completes, regardless of its recommendation.

“No new independent evidence” is normalized as “no new canonical evidence unit” across evidence families. For reported news, novelty means a new known independence group not present before the action. For direct primary/authority evidence, it means a new canonical asset/content version. For structured evidence, it means a new stable `fact_id`. Unknown-lineage news does not count as new independent support. This prevents macro/fundamental actions from being falsely classified as empty merely because independence groups apply only to reported news.

## 21. Round-Two Analyst

Round 2 uses the same Analyst prompt family, schema, status policy, and model role. Its input is a newly built ContextPack over the merged immutable EvidenceState, plus bounded prior normalized hypotheses/conflicts/gaps and the corrective-result summary. It does not receive hidden round-1 reasoning.

The Analyst must be free to reject, revise, promote, downgrade, replace, or retain hypotheses. The prompt must not characterize retrieved evidence as confirmation. Round 2 can return `READY` or `ABSTAIN`. A valid `FOLLOW_UP` value is recorded as a round-exhaustion semantic violation and normalized without a third Analyst call.

Artifacts record hypothesis-set changes, disposition changes, conflict changes, status/type changes, executed action fingerprint, and new canonical evidence-unit count.

## 22. Judge Migration

The production `Judge` LLM node is removed. Its responsibilities migrate as follows:

| Judge behavior | Destination |
|---|---|
| Generate causal hypotheses | Evidence Analyst |
| Relate evidence to hypotheses | EvidenceDecision plus normalization |
| Choose primary/secondary causes | Analyst proposal constrained by ClaimPlan |
| Rank hypotheses | Deterministic role/order policy, not confidence scoring |
| Generate `summary_md` | Streaming Writer |
| Calculate grounding rate | Structural assurance/evaluation |
| Format evidence content | Phase 3 ContextPackBuilder |
| Hash/fidelity helpers | Phase 3 artifact identity and assurance |
| Failure fallback to insufficiency | Removed; technical errors fail the run |

`nodes/judge.py` must not remain imported by the production graph or hidden behind a compatibility flag. Legacy behavior is preserved only through frozen fixtures and offline evaluation adapters.

## 23. ClaimPlan

`ClaimPlan` is the deterministic, pre-validation public claim proposal. Each claim includes:

- deterministic `claim_id` derived from run, assessment, hypothesis, and role;
- source `hypothesis_id` where applicable;
- role: `PRIMARY`, `SECONDARY`, `CONTEXT`, or `LIMITATION`;
- exact bounded statement and optional mechanism copied from normalized Analyst output;
- allowed support and contradiction evidence IDs;
- magnitude fit and conflict references;
- required citation IDs; and
- deterministic ordering metadata.

The plan also includes candidate final status/type, assessment hash, ContextPack/EvidenceState identity, required limitations, and plan hash. It contains no confidence score and no Writer-authored text.

## 24. ClaimPlan Construction

Construction rules are deterministic:

1. accept only normalized hypotheses with semantic support;
2. permit at most one `PRIMARY` claim;
3. intersect hypothesis support IDs with accepted Analyst `SUPPORT` decisions;
4. allow `WEAK` evidence only for context, never causal sufficiency;
5. downgrade or omit roles that exceed source, conflict, or status constraints;
6. copy statements/mechanisms without inventing causal detail;
7. generate limitations from unresolved conflicts and typed data/capability gaps using fixed templates;
8. order primary, secondary, context, then limitations with stable tie-breaking; and
9. set candidate status to the lower of normalized recommendation and status ceiling.

A bounded negative `NO_MATERIAL` claim is created only after the gates in Section 15 pass. Otherwise coverage gaps become limitations under an `ABSTAIN` result, not a negative causal assertion.

## 26. ClaimValidator

`ClaimValidator` is deterministic and never invokes a model. It checks:

- every evidence/citation ID exists, is eligible, belongs to the run/snapshot, and matches canonical hash/state;
- every causal claim has accepted semantic support bound to its hypothesis;
- evidence role and materiality permit the proposed claim role;
- `SUFFICIENT` satisfies primary-grade or known-independent-report corroboration rules;
- magnitude fit supports the claimed role;
- unresolved contradictions/conflicts do not defeat the claim;
- structured facts match the asserted direction and time scope;
- required context gates and limitations are present;
- attribution type and status do not exceed the normalized ceiling; and
- runtime, policy, schema, plan, and artifact identities are coherent.

Missing/cross-run IDs, hash mismatch, snapshot mismatch, unsupported schema, or corrupt canonical state fail the run as `CLAIM_INTEGRITY_FAILURE`. Valid but insufficient attribution support causes a claim drop or role/status downgrade; if no publishable causal claim remains, the result becomes `ABSTAIN`. Diagnostics are not Writer-visible.

## 27. ValidatedClaimPlan

`ValidatedClaimPlan` contains only the maximum public claim surface:

- valid ordered claims;
- final deterministic status and normalized attribution type;
- required limitations;
- exact citation map;
- permitted claim IDs and evidence IDs;
- source-role and independence summary needed by assurance;
- input artifact identities; and
- validated-plan hash.

Dropped-claim diagnostics, rejected hypotheses, ambiguous links, internal ceiling calculations, and policy violations are persisted separately for observability but are excluded from `WriterInput`.

## 28. Writer Boundary

The Writer receives exactly `final_status`, `attribution_type`, the deterministic `observed_move`, the `ValidatedClaimPlan`, narrowly bound supporting snippets, the citation map, required limitations, the required section/format contract, and bounded style instructions. It may paraphrase, organize, and connect already validated claims. It may not:

- retrieve or request evidence;
- add facts, hypotheses, mechanisms, causes, certainty, or citations;
- change claim roles, attribution type, or status;
- omit required limitations;
- cite an ID outside the validated citation map; or
- expose internal policy, diagnostics, prompts, or rejected hypotheses.

Writer-visible claim/citation markers may be required in the model output to make deterministic assurance possible. Presentation-layer removal or rendering belongs to Phase 5, not this specification.

## 29. Finalizer Migration

The current Finalizer ranks hypotheses and recomputes status, including fallback inference from Critic and cause state. Those semantic behaviors are removed.

The V1.1 Finalizer is a small terminal runtime wrapper after successful structural assurance. It persists the immutable result envelope, final status/type, output artifact ID/hash, provenance references, timing/token accounting, and completion state. It cannot rank, repair, rewrite, infer a status, or turn a failure into `ABSTAIN`.

## 30. Streaming Writer

The Writer uses the provider's real streaming interface (`stream`/`astream`), never a post-hoc fake chunker.

Conceptual interface:

```text
StreamingWriter.stream(
    writer_input: WriterInput,
    cancellation: CancellationToken,
) -> Iterator[WriterDelta]
```

The adapter requires declared streaming capability, bounded timeout, cancellation propagation, token accounting, and a terminal completion event. Before the first emitted delta, one technical retry is allowed for transport/timeout failure using the identical WriterInput. After any delta is emitted, any transport, timeout, cancellation, or provider failure fails the run; the runtime must not silently replace or continue the provisional response.

All deltas are provisional until structural assurance succeeds. Phase 4 defines the semantic/runtime contract only; client transport and SSE framing are Phase 5 concerns.

## 31. Structural Assurance

Assurance is deterministic and performs no model call or rewrite. It verifies:

- stream reached a valid terminal completion;
- required sections and required limitations exist;
- every emitted citation ID resolves to the validated map and current run;
- emitted claim/citation markers are subsets of allowed IDs;
- output status/type match the ValidatedClaimPlan;
- no required primary/limitation content was omitted;
- WriterInput, plan, evidence, runtime, and output artifact hashes align; and
- timeout, cancellation, token, and completion metadata are internally consistent.

Assurance cannot prove every paraphrase semantically equivalent; the bounded WriterInput and marker contract reduce that risk. Any assurance failure invalidates the provisional output and fails the run as `ASSURANCE_FAILED`. No answer is published and no repair call occurs.

## 34. Final Semantic State Machine

```text
COLLECTING
  ├─ integrity/technical failure → FAILED
  └─ evidence ready → ANALYZING_R1

ANALYZING_R1
  ├─ technical schema/transport failure → one retry → FAILED if exhausted
  ├─ READY or ABSTAIN → PLANNING
  └─ FOLLOW_UP
       ├─ executable unique batch → CORRECTING
       └─ no executable batch → normalize READY/PARTIAL or ABSTAIN → PLANNING

CORRECTING
  ├─ cancellation/integrity failure → FAILED
  ├─ retrieval degradation/no new unit → ANALYZING_R2 with explicit result
  └─ merged evidence → ANALYZING_R2

ANALYZING_R2
  ├─ technical failure → one retry → FAILED if exhausted
  └─ READY/ABSTAIN/FOLLOW_UP-normalized → PLANNING

PLANNING → VALIDATING
  ├─ integrity failure → FAILED
  ├─ no publishable causal claim → WRITING_ABSTENTION
  └─ validated plan → WRITING

WRITING / WRITING_ABSTENTION
  ├─ pre-delta technical failure → one retry
  ├─ post-delta failure/cancel → FAILED
  └─ complete provisional output → ASSURING

ASSURING
  ├─ structural failure → FAILED
  └─ pass → COMPLETED
```

`ABSTAIN` is a completed epistemic result only after a valid Writer and assurance path. It is never a synonym for `FAILED`.

## 39. Test Strategy

**Schema and retry tests**

- strict extra-field, enum, reference, duplicate-ref, and max-three rejection;
- exactly one technical retry and identical semantic input hash;
- no retry for valid `ABSTAIN`, semantic inconsistency, or unavailable backend;
- no regex salvage/coercive parsing.

**Normalization and ceiling tests**

- support/contradiction pair handling, role downgrades, conflict outcomes, and model-lower-only status;
- primary/direct and two-independent-report paths to possible `SUFFICIENT`;
- unknown-lineage, commentary-only, unresolved conflict, and one-report ceilings;
- all `NO_MATERIAL` gates, including missing benchmark/sector context;
- `FOLLOW_UP` without gap/intent, unsupported backend, non-recoverable market structure, duplicate action fingerprint, and system failure remaining failure; and
- company-vs-sector, macro-vs-company, contradiction, and unsupported-market-structure hypothesis fixtures.

**Corrective tests**

- reason-to-need mapping, backend capability, hint sanitization, stable IDs/fingerprints, repeat refusal, deadlines, cancellation, and empty-batch rejection;
- novelty rules for news, primary documents, macro/fundamental facts, and unknown lineage;
- round 2 cannot trigger a third Analyst call and can reverse round-1 conclusions.

**Claim and Writer tests**

- deterministic plan hashes/order, one primary maximum, no invented mechanism, limitation templates, source-role gates, citation resolution, and integrity failure paths;
- Writer receives only ValidatedClaimPlan public fields;
- real provider-stream adapter contract, one pre-delta retry, no post-delta retry, cancellation, and token accounting;
- assurance rejects unknown IDs, missing limitations/sections, mismatched status, incomplete stream, and hash mismatch.

**Graph and regression tests**

- exact call counts: two normal, three with correction, plus only allowed technical retry attempts;
- no production imports or routes to Judge, `expand_macro`, LLM Validator repair, or fake streaming;
- epistemic `ABSTAIN` remains distinct from technical `FAILED`;
- frozen legacy fixtures remain readable through offline/versioned adapters.

Pure schema, normalization, ceiling, corrective construction, claim construction/validation, novelty, assurance, and state-transition tests use no model or provider. Provider integration tests cover native structured output, fallback strict parsing, real streaming, usage metadata, cancellation, and timeout behavior. End-to-end graph tests use deterministic fake providers and canonical retrieval fixtures; live-provider tests remain opt-in.

## 44. Final Feasibility Verdict

1. **Can the current Critic realistically evolve into the V1.1 Evidence Analyst?** Yes, as a rename/rewrite at the same first semantic boundary. Its current model invocation, prompt loading, evidence-ID exposure, and tracing seams are reusable; its response and decision contracts are not.
2. **Which Critic behavior should survive?** Bounded evidence presentation, one semantic call, stable evidence references, technical-attempt accounting, and artifact emission. Scalar chunk grading, count-based sufficiency, regex salvage, prompt-shrinking retry, and raw next-action ownership must not survive.
3. **Is the current Judge still needed as an LLM node?** No. Current code shows Judge both creates hypotheses and final prose, duplicating the new Analyst and Writer responsibilities and consuming the second call needed by Writer.
4. **What exact current Judge behavior is reused elsewhere?** Evidence formatting moves to ContextPackBuilder; causal drafting moves to Analyst; role projection moves to ClaimPlan; grounding/citation metrics move to assurance/eval; prose moves to Writer; content hashes move to artifact identity. Its model call and failure-to-abstain fallback are deleted.
5. **Can Validator become deterministic ClaimValidator without losing important safety?** Yes. Existing evidence-ID, cutoff, source-role, independence, prerequisite, and structured-direction checks are deterministic. The unsafe portions are LLM repair and semantic enrichment, not the gates.
6. **Can `expand_macro` become a generic one-action corrective path using the existing retrieval stack?** Its node cannot safely be generalized, but its goal can: typed gap/action construction can call the same Phase 3 canonical retrieval executor. Macro series/fundamental adapters need wiring; sector and macro-event text remain capability-gated.
7. **Is `AnalystDecision → EvidenceAssessment` normalization fully deterministic?** Yes. Every input is a parsed decision, canonical artifact, capability registry, or versioned policy; identity assignment, gap mapping, sanitization, fingerprints, ceiling, and route normalization require no model judgment.
8. **Can status ceilings be computed without stealing semantic reasoning from the Analyst?** Yes. The Analyst alone declares semantic support/contradiction and hypotheses. Code only applies canonical eligibility, materiality, role, lineage, conflict, coverage, and magnitude-fit gates to those declarations.
9. **Can the normal path genuinely be reduced to two logical model calls?** Yes. Removing Judge and Validator repair leaves one Analyst call and one Writer call; ClaimPlan, validation, assurance, routing, and finalization are deterministic.
10. **Can the corrective path genuinely remain three logical calls?** Yes. One action executes without a model, then the same Analyst runs once over cumulative evidence before the single Writer call. Round exhaustion forbids a third Analyst call.
11. **Does any Frozen V1.1 semantic contract remain unrealistic after Phases 2–3?** The architecture is realistic, but some outcomes are not currently supportable: the promoted snapshot lacks production benchmark/sector context, macro-event text is thin, and structured macro/fundamental retrieval still needs adapters. Those conditions force gaps/downgrades rather than architectural exceptions.
12. **What narrow contract clarifications should be carried to final integration?** Use canonical evidence-unit novelty across evidence families; scope independence groups to reported news; separate material-capable from semantically supported counts; use `SessionAlignment`; distinguish data from capability gaps; define conservative tokenizer behavior; and resolve neutral `attribution_type` semantics for coverage-driven `ABSTAIN`.

Overall verdict: **feasible with a deliberate semantic cutover, not an additive wrapper around the current MCJ path**. The principal blockers are contract finalization and missing context capability, not model-interface availability.

## 45. Narrow Contract Clarifications

1. The Frozen phrase “no new independent evidence” should mean “no new canonical evidence unit” at the generic corrective boundary. Independence groups apply specifically to reported news; direct documents and structured facts use canonical versions/fact IDs.
2. `material_evidence_count` should be interpreted as material-capable evidence count until semantic support is established; the post-Analyst count is accepted material support count.
3. `independent_report_count` means eligible known-lineage reported-news group count, not raw article count.
4. Session co-movement should use the Phase 3 `SessionAlignment` contract rather than an untyped boolean.
5. Data absence and capability absence are separate typed gaps because only the latter determines whether correction is executable.
6. Exact token guarantees are possible only for declared model/tokenizer pairs. Other adapters must use a conservative byte upper bound or reject unsupported exact-budget mode.
7. The Frozen `AttributionResult` requires `attribution_type`, but coverage-driven `ABSTAIN` does not safely fit either a causal type or `NO_MATERIAL`. Final integration should either permit a null type for abstention or add a neutral non-assertive value; implementation must not silently label inadequate coverage as `NO_MATERIAL`.

## 46. Open Questions for Phase 5

- How should provisional deltas be labeled and invalidated over the selected client transport?
- Does the client buffer until assurance or render provisional content with an explicit pending state?
- What terminal event distinguishes assured completion from post-delta failure?
- How are cancellation acknowledgements and partial-output invalidation represented?
- Which claim/citation markers remain in transport payloads, and where are they converted to presentation links?
- How should reconnect/resume behave when the Writer completed but assurance has not?
- What UI language distinguishes epistemic `ABSTAIN`, degraded `PARTIAL`, and technical `FAILED` without exposing internal diagnostics?
- What retention policy applies to provisional deltas that fail assurance?

These are transport and presentation questions. They do not change the Phase 4 semantic ownership, retry, call-budget, or artifact contracts.
