## 1. Lock item A — Exact identity formulas

Every ID below is produced by new builder functions in `packages/data-core/catalyst_data/canonical/ids.py` (docs-only name; no code written in Phase 0) that evolve the existing primitives listed per item. No competing ID system is created.

**Shared canonical serialization (evolve `manifests/universe.py:canonical_json_bytes` / `sha256_identity`):**

- Encoding: `json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(",", ":")).encode("utf-8")`, then `hashlib.sha256(...).hexdigest()` (lowercase, 64 hex).
- Null representation: **JSON `null`** for every optional/unknown input; keys are never omitted and never replaced with `""`. Empty string is reserved for genuinely empty text values (e.g., empty title), never for "unknown".
- UNKNOWN vs missing: both serialize as `null`. A builder never distinguishes them inside the hash payload; the projection layer records a typed reason column (e.g., `eligible_at_reason`) where the distinction matters.
- All normalization is applied **before** building the hash payload.

**A.1 `asset_id` (== `canonical_asset_id`; serialized field is exactly `asset_id`, no alias — M2 `canonical/model.py:CanonicalAsset.asset_id`, Final TSD §5.2).**

- Namespace/prefix: `v1:asset`. Final format: `v1:asset:{sha256_identity(payload)}` (prefix + 64 hex).
- Ordered input fields (dict keys sorted by canonical serialization; order in the list below is the semantic order, not the serialization order):
  - NEWS: `namespace="v1:asset"`, `asset_type="NEWS"`, `subtype="article"`, `article_id=<normalized articles.article_id>` (existing `articles.py:compute_article_id` value `{provider}:{native_id}`, unchanged — stable within provider scope per data-core TSD §10).
  - FILING: `namespace="v1:asset"`, `asset_type="FILING"`, `subtype="filing"`, `cik=<normalized CIK>`, `accession_number=<normalized accession>` (Final TSD §5.2: SEC filing identity is accession-based).
  - OFFICIAL_RELEASE / STRUCTURED_CONTEXT: **no assets of these types are minted in M3** (see §C).
- Normalization: ticker → uppercase, stripped; CIK → numeric string zero-padded to 10 digits (SEC convention; current `filings.cik` values are already zero-padded, e.g., `0000320193`); accession → stripped, case preserved (digits + hyphens, opaque); article_id → `{provider}:{native_id}` with provider lowercased.
- Collision: backfill fails closed if two subtype rows produce the same `asset_id` but differ in any projected field. Same identity payload from the same row is idempotent.
- Stability: `asset_id` never changes on corpus rebuild or content change (content change creates a new content version ID, never a new asset ID — Final TSD §5.2).
- Missing input (no article_id / no accession): row is **not** backfilled as a canonical asset; recorded in the audit `excluded_assets` count (fail closed, never synthesized).
- Legacy `storage/sqlite.py:compute_asset_id(ticker, date, source_type)` (`SHA-256("ticker|date|source_type|v1")`, `storage/sqlite.py:204-210`) is **unsuitable** for V1.1 canonical assets: it is ticker/date/source-type based, not subtype-identity based, and would break when content or corpus changes. It is **retained as legacy** for raw/clean asset addressing and is not used by the canonical backfill.

**A.2 `canonical_content_version_id`.**

- Namespace/prefix: `v1:content`. Final format: `v1:content:{sha256_identity(payload)}`.
- Payload: `{"namespace":"v1:content","asset_id":..., "content_hash":..., "normalizer_version":..., "materiality_version":..., "version_ordinal": n}`.
- `content_hash` = `sha256(normalized_content_text.encode("utf-8"))` (64 hex), where normalized content text uses the corpus normalizer `_normalize_text` (`corpus/news_v2.py:25-30`): NFC, `\r\n|\r → \n`, per-line `[ \t]+ → " "` with `rstrip`, blank-line runs collapsed to `\n\n`, final strip.
- `normalizer_version`: per-subtype builder identity, e.g., `"sec_extract_v1"` (filing reparse parser version, M3-4) and `"news_body_v1"` (news body recovery version, M3-5). Any parser/body-recovery change bumps this string and therefore the content version.
- `materiality_version`: content-state classifier version, e.g., `"materiality_v1"` plus `parse_quality` value; changing materiality rules bumps the version.
- `version_ordinal`: 1-based per asset; a content change (new `content_hash` or new normalizer/materiality version) inserts ordinal+1. **Idempotency:** the same asset+content_hash+normalizer_version+materiality_version always yields the same `canonical_content_version_id` and reuses the existing version row; reruns never bump ordinals.
- Collision/duplicate: two version rows with the same version ID are merged (UNIQUE on `(asset_id, canonical_content_version_id)`); a same-version-ID row with a different `content_hash` is a hard failure.

**A.3 `corpus_document_id`.**

- Final format: 64 lowercase hex (must satisfy the existing `corpus/persisted_id.py:is_valid_persisted_document_id`).
- Payload: `{"corpus_document":"v1","content_version_id":..., "chunk_profile_version":...}` (data-core TSD §12: derived from content version and chunk profile version).
- Evolves: the corpus `document_id` field; current filing `document_id` values (v13) are already 64-hex and remain valid under the validator.

**A.4 `chunk_id`.**

- Final format: `{corpus_document_id}:{chunk_profile_version}:{section_key}:{ordinal}` — evolves the current grammar `{document_id}:{profile_version}:{section_key}:{ordinal}` (`corpus/news_v2.py:138`, `filing_v3.py`), with `document_id` replaced by the canonical `corpus_document_id`.
- `chunk_profile_version`: `"news_v2"` / `"filing_v3"` (unchanged constants) or their successors; `section_key`: normalized by `filing_v3._section_key` (lowercase alnum/underscore) or `"body"` for news; `ordinal`: zero-padded `ORDINAL_WIDTH=4`.
- The Final TSD §5.2 requirement that chunk identity be derived from content version, corpus document/profile, section, ordinal, and content hash is satisfied transitively: `corpus_document_id` is derived from `content_version_id`, which is derived from `content_hash`.
- Collision: fail closed on `UNIQUE (build_id, document_id, chunk_profile_version, section_key, ordinal)` (`corpus/streaming_publication.py:221`); identical input always yields identical `chunk_id`.

**A.5 `fact_id`.**

- **NONE IN M3.** No structured-fact canonical assets are projected in M3 (§C). The M2 `StructuredEvidenceIdentity` contract (`canonical/model.py`) remains; no `fact_id` rows are minted until the structured-context milestone (M4/M5).

**A.6 `build_id`.**

- Final format: 64 lowercase hex. Evolving `corpus/manifest.py:compute_manifest_id` (already `sha256` over the canonical manifest identity payload with `sort_keys`/`(",",":")`, excluding `created_at`).
- Payload: `{"normalization_version","chunk_profile_versions","source_classifier_version","certified_snapshot_identity","sorted_active_chunk_inventory","tokenizer_revision","embedding_revision_or_null"}` — exactly the current `compute_manifest_id` identity fields (`corpus/manifest.py:65-79`).
- Reproducibility: identical canonical projection + profile versions → identical `build_id`; a corpus rebuild never mints a new `asset_id`.

**A.7 `dedup_cluster_id`.**

- Namespace/prefix: `v1:dedup`. Final format: `v1:dedup:{sha256_identity(payload)}`.
- Payload: `{"algorithm":"catalyst_dedup_v1.0","members":[sorted canonical asset_ids of the connected component]}`.
- Deterministic given the same input graph; singleton assets (no relation) still receive a cluster ID so dedup identity coverage is measurable. Ambiguous lineage is never treated as independence (§G).

**A.8 `independence_group_id`.**

- Namespace/prefix: `v1:independence`. Final format: `v1:independence:{sha256_identity(payload)}`.
- Payload: `{"algorithm":"catalyst_independence_v1.0","members":[sorted canonical asset_ids]}`.
- Only `reported_news` assets with known lineage receive an `independence_group_id`; unknown-lineage assets get `NULL` and increment `unknown_independence_asset_count` (Frozen §6; M3-6).

## 2. Lock item B — Canonical schema ownership (v14 `canonical_registry`)

**content_hash ownership decision:** `canonical_assets.content_hash` is a **non-authoritative cached copy of the current content-version hash** (option 2 in the lock list). The single authority is `canonical_content_versions.content_hash` (Final TSD §5.2 "Normalized content hash is owned at the canonical content-version layer"). M3-1's list of `content_hash` on `canonical_assets` is therefore implemented as a cache/contract-projection only: backfill copies the hash of the asset's highest-`version_ordinal` content version; content-version writes own the hash; dedup/content identity never reads `canonical_assets.content_hash` as authority. The M2 contract field `CanonicalAsset.content_hash: str | None` remains exactly as shipped.

**v14 DDL** (applied by a new `Migration(version=14, name="canonical_registry", ...)` appended to `MIGRATIONS` in `packages/data-core/catalyst_data/migrations.py`, with the v13 savepoint/idempotency pattern; **never** added to `storage/sqlite.py` initial DDL):

```sql

    provider              TEXT NOT NULL,
    publisher             TEXT,
```

**Association/subtype link rules (M3):**
- `articles` → one NEWS asset per `articles.article_id` (`subtype_table='articles'`, `subtype_pk='article_id'`).
- `filings` → one FILING asset per `filings.filing_id` (`subtype_table='filings'`, `subtype_pk='filing_id'`); filing assets keyed by CIK+accession (A.1).
- `filing_documents` → **content versions/sections of the parent FILING asset, not separate assets** (Final TSD §5.2: documents/sections are versioned by accession, document, parser version, section key, ordinal). `canonical_subtype_assoc` maps each `filing_documents` row to its parent asset (`subtype_table='filing_documents'`, `subtype_pk='document_id'`) as a content-version provenance row; the association row's parent asset is the filing asset.
- `canonical_asset_links` is the raw relation edge table consumed by dedup/independence (§G); allowed `link_type` values are the CHECK set above. UNIQUE pair enforced by PK.
- `canonical_asset_tickers` mirrors `article_tickers` and `filings.ticker` per asset.

**Migration idempotency / rollback:** `run_migrations()` twice → `PRAGMA user_version` stays 14, no duplicate-column errors (v13 savepoint pattern, `migrations.py:1088-1194`). Rollback boundary: additive DDL only; rollback drops only the five new tables above, in reverse dependency order (`canonical_asset_links`, `canonical_subtype_assoc`, `canonical_asset_tickers`, `canonical_content_versions`, `canonical_assets`); never drops historical/raw/subtype tables.

## 4. Lock item D — Temporal and SEC rules

**Accepted-time source priority** (`sec/accepted_time.py`, M3-3; read-only sample verified):

1. EDGAR submissions JSON (`raw_assets.source_type='sec_filings'`): parse `recent.accessionNumber`, `recent.filingDate`, `recent.reportDate`, `recent.acceptanceDateTime` as parallel arrays; the accepted time for accession `A` is `recent.acceptanceDateTime[i]` where `recent.accessionNumber[i] == A` (index-aligned). Verified present in 158/6,227 archived payloads; recovery is per-accession, not per-payload.
2. EDGAR index-headers HTML (`*-index-headers.html`/`.htm`): parse the `Accepted` field when the payload is retained in the archive (no such payloads currently retained; parser target locked for reimport).
3. Filing index HTML (`*-index.html`) and primary document headers: **do not** carry authoritative accepted time; used only as fallback evidence of `filed_at` date, never as accepted time.
4. `filings.filed_at`: date only; **never silently coerced to 16:00** (Final TSD §5.2; M3-3 negative test).

**Timestamp parsing / normalization:** parse ISO-8601 with `Z` or explicit offset; normalize to UTC second-resolution `YYYY-MM-DDTHH:MM:SSZ` via `timeutil.normalize_utc_second_z` (naive → treated as UTC by that contract; rejected if malformed). `TemporalIdentity` already requires timezone-aware UTC (`canonical/temporal.py`).

**Accepted-time provenance:** recorded per asset (`accepted_time_recovered=1`, `temporal_precision='accepted_time'`, `eligible_at_reason='accepted_time_recovered'`) and per content version.

**Behavior when time-of-day is absent:** default **fail closed** (Final TSD §5.2): `eligible_at = NULL`, `temporal_precision='unknown_time_of_day'`, `fail_closed=1`, `eligible_at_reason='fail_closed_no_time_of_day'`. Under an operator-approved declared conservative rule (Q-005), `eligible_at = latest_plausible_instant(date)`.

**`derive_eligible_at` typed result** (`sec/eligible_at.py`): a frozen dataclass with exactly:

```python
@dataclass(frozen=True)
class EligibleAtResult:
    eligible_at: datetime | None          # None => not eligible
    eligible_at_reason: str               # vocabulary below
    temporal_precision: str               # vocabulary below
    accepted_time_recovered: bool
    fail_closed: bool
```

**`eligible_at_reason` vocabulary:** `accepted_time_recovered` | `publication_time_provider` | `ingestion_time_conservative` | `fail_closed_no_time_of_day` | `fail_closed_no_accepted_time` | `latest_plausible_approved` | `not_eligible`.

**`temporal_precision` vocabulary:** `accepted_time` | `publication_time` | `ingestion_time` | `date_only_latest_plausible` | `unknown_time_of_day` | `unknown`.

**Latest-plausible-instant fail-closed rule:** `latest_plausible_instant(d)` = `(d + 1 day) 00:00:00 America/New_York` converted to UTC — the instant at which date `d` ends in ET. This is the declared conservative rule (data-core TSD §7 "eligible only after the latest plausible instant consistent with the precision"). Example: Monday 2026-01-05 (EST, UTC-5) date-only → `latest_plausible_instant = 2026-01-06T05:00:00Z` (next-day 00:00 ET), which is after Monday's 16:00 ET close and before Tuesday's close → eligible for the Tuesday window, matching the M2 test `test_monday_1605_earnings_eligible_for_tuesday_window_via_calendar`. For an EDT date (e.g., 2026-05-01) the instant is next-day `04:00:00Z`. Rule requires operator approval before fail-closed rows count in DATA-01 numerator (Q-005).

**Weekend / holiday / premarket / after-close:** use `trading_calendar.py` (`is_trading_day`, `session_close_utc`, `calendar_trading_days`, `CALENDAR_YEARS` 2024–2027) and `retrieval/cutoff.py` `ExchangeCutoffPolicy`/`compute_cutoff`. After-close acceptance (e.g., Monday 16:05 ET) is eligible for the Tuesday window (`information_window_start_at = Monday close`, `cutoff_at = Tuesday close`). Friday after-close → Monday window (prior-session via calendar, never calendar-day subtraction).

**Q-005 operator approval:** required before any fail-closed row (`unknown_time_of_day` / `date_only_latest_plausible`) counts toward the DATA-01 numerator. Default is fail closed per Final TSD §5.2.

## 9. Lock item I — Promotion and rollback protocol

Corpus/FTS pointers live in SQLite; dense `active_generation` is a filesystem pointer. They are **not** one cross-medium atomic operation. `index/v1_promote.py` + `scripts/promote_v1_1_generation.py` (M3-10/M3-12) implement the staged protocol:

**Pointers (exact):**
- served corpus relation / corpus_manifest: `corpus_manifest.is_current` + `corpus_served_chunks.manifest_id` (SQLite);
- lexical_index_state: `mode_served`, `corpus_manifest_id`, `lexical_generation_id`, `lexical_digest`, `row_count` (SQLite singleton row);
- active_generation.json: `data/lancedb_gold/<source_bundle_id>/active_generation.json` (filesystem; schema `active_generation_v1`);
- index manifest / source bundle IDs: `IndexManifest` (`retrieval/index_manifest.py`) + `active_generation.json` fields (`index_manifest_id`, `source_bundle_id`, `table_name`).

**Staged order (locked):**
1. Preflight and source hashes (snapshot SHA, corpus manifest, canonical audit gates, DATA-01 report).
2. Build state: new `corpus_publication_builds` row (`build_id` from A.6), `corpus_build_*` rows under the new build ID; FTS generation; dense source bundle + staging table.
3. Validation state: row counts, digests, chunk/vector identity parity, gates.
4. Promotion order: **(a)** SQLite corpus publication (`corpus_manifest` flip + `corpus_served_chunks` manifest_id in one transaction, `corpus/manifest.py:publish_manifest` pattern); **(b)** SQLite lexical_index_state update (single transaction, `retrieval/fts5_builder.py:build_fts5_index` upsert pattern); **(c)** dense pointer file write (filesystem: tmp + `fsync` + `os.replace`, prior directory untouched — `retrieval/gpu_contract.py:_atomic_json` pattern).
5. Durable promotion journal: `data/manifests/m3_promotion_journal.json`, schema `m3_promotion_journal_v1`: `promotion_id`, `build_id`, `corpus_manifest_id`, `lexical_generation_id`, `lexical_digest`, `dense_index_manifest_id`, `active_generation_path`, `prior_*` pointer backups, per-step status (`pending|done`), timestamps, source hashes. Written with `fsync` (file + directory) before the first pointer flip and after each step.
6. Crash recovery at every boundary: read journal; resume the first `pending` step; a step recorded `done` is never re-executed; a partially written dense file (tmp only) is discarded.
7. Pointer backup: `prior_*` fields in the journal capture the exact prior pointers (corpus manifest ID, lexical row, active_generation bytes).
8. Post-promotion verification: served chunk count == FTS row count == dense vector count; `DataRuntimeIdentity` emits actual loaded versions.
9. Rollback order: reverse of promotion — restore dense pointer from backup first, then lexical_index_state, then corpus_manifest (each idempotent; journal `rollback` state). Rollback restores pointers; it **does not** git-revert the DB and never touches raw/frozen/prior generation.
10. Idempotent rerun: rerunning with the same `build_id`/manifest IDs re-verifies and is a no-op if already promoted.
11. Cross-medium failure: if dense succeeds but SQLite promotion fails, the dense pointer file is rolled back to backup and the SQLite steps re-run (journal decides; partial dense is never left active). If SQLite promotion succeeds but dense fails, the SQLite generation is valid and remains promoted while dense stays prior; the promotion is marked FAILED (not partial success), and the operator either completes dense (idempotent import) or rolls back SQLite pointers.

Raw archives, frozen snapshot, and previous generation remain immutable; prior generation retained through the rollback window.
