## 2. Execution conventions (applies to every milestone)

1. **Test-first.** Every implementation task starts with a failing test (FAST tier when possible), runs it to see it fail, implements minimally, re-runs, then commits. Tests are the deliverable; code is what makes them pass.
2. **Test tiers** (Final TSD §24): FAST = no models/GPU/production data; MEDIUM = SQLite + bounded fixtures/fake providers; EXPENSIVE = real provider/GPU/promoted data/Stage-1+.
3. **Fixture policy.** Deterministic fixtures in each package's `tests/fixtures/`. Never commit provider credentials, raw licensed payloads, DBs, embeddings, or local run artifacts (root `.gitignore` already excludes most; keep it that way).
4. **Package direction.** `app → agents → data-core`; `eval` is an offline consumer. No new generic contracts package. No eval import into agents (boundary tests in `packages/agents/tests/test_package_boundaries.py` enforce this).
5. **Model-call budget.** Normal = 1 Analyst + 1 Writer = 2 logical calls. Corrective = 2 Analyst + 1 Writer = 3. One technical retry only (transport/timeout/invalid structured schema, identical semantic input). No retry for semantic dissatisfaction/PARTIAL/ABSTAIN.
6. **Persistence.** SQLite is authoritative for run state/events/artifacts/structured context. LanceDB only serves dense vectors. Connection-per-operation (Final TSD §16). No `sqlite3.Connection` crosses threads or lives in cached deps.
7. **Public names.** Frozen public event names are `sequence` and `emitted_at`; internal DB columns may stay `event_seq`/`seq` and `occurred_at` but never surface as competing aliases (API-01 lock).
8. **Do-not-build list** (Final TSD §30): no Planner, always-on web search, market-structure provider, second corrective round, production two-action default, multi-agent/supervisor, free ReAct, GraphRAG, memory, MCP, SQL/tool agent, microservices, Redis/Celery/Kafka/Temporal, semantic context compressor, publisher authority score, enterprise auth/RBAC, WebSocket, second production graph, second event store, generic contracts package, frontend-generated attribution semantics.
9. **Secrets.** Credentials stay in `RuntimeCredentialStore` (memory only), never persisted, never logged, redacted from artifacts/reports (existing `trace-redaction.test.ts` and user-smoke secret scans are the precedent).
10. **Commit discipline.** Small reviewable commits; conventional messages (see §4.5 of this file). Do not split one atomic correctness change merely for commit count; do not lump unrelated changes.
11. **Frontend verification path.** `apps/workbench` has no test-runner dependency and no `test` script today; existing tests use Node's built-in `node:test`. Use `cd apps/workbench && node --experimental-strip-types --test "src/**/*.test.ts"` (Node ≥ 22). M6-10 adds the `"test"` npm script explicitly. Do not introduce Vitest.

### 3.4 Staging policy

- Stage only intended files: `git add <specific file paths>`. Never `git add .`, never `git add -A` (including path-prefixed `git add -A <dir>`), and never package-level broad adds such as `git add apps/workbench/src`. For deletions use `git rm <explicit files>`; for mixed files use `git add -p`; for tracked deletions/modifications inside a directory use an explicit per-file list.
- Use `git add -p` when a file mixes intended and unrelated edits (common for `state.py`, `schemas.py`, `graph.py` during M5/M6).
- Before every commit:
  ```bash
  git diff                  # unstaged review
  git diff --cached         # staged review (exactly what will commit)
  git diff --check          # whitespace errors
  ```
- Prevent unrelated docs/data/scratch from entering commits: `scratch/` stays untracked; generated DB/index/embedding artifacts stay ignored (root `.gitignore`); `data/baseline/reports/*` small JSON/Markdown reports are intentionally committed, `data/baseline/stores/*` is not.

### 3.5 Commit strategy

- Each plan task defines a coherent commit boundary. Prefer the pattern: `test:` (failing test) → `feat:`/`fix:` (implementation) → `refactor:`/`chore:` (migration/cleanup) when the change is large; commit test+implementation together when the test is the contract (common in M2 schema tasks).
- Commit message convention (repo precedent, e.g. `docs(architecture): freeze Catalyst vNext V1`):
  ```
  <type>(<scope>): <summary>

  <optional body: what/why, TSD § reference, exit-gate evidence>
  ```
  Types: `feat`, `fix`, `test`, `refactor`, `chore`, `docs`, `data`, `revert`.
- One logical change per commit. Do not split an atomic correctness change; do not bundle unrelated cleanup into a feature commit.

### 3.8 Data / index migrations — rollback separation

Git history is **never** a substitute for versioned DB/index rollback. Keep four independent rollback planes:

1. **Source-code rollback:** `git revert` of milestone merges on `v1.1/integration`; sealed baseline references preserved via tags (`v1.1-m1-baseline`) and the M1 baseline report.
2. **DB/schema migration rollback:** additive/versioned migrations (`packages/data-core/catalyst_data/migrations.py` precedent); each migration is reversible or paired with a prior snapshot; never destructive in-place mutation of `raw_assets`/historical tables.
3. **Corpus/FTS/dense generation rollback:** build the new generation beside the current one (new build ID / new index manifest / new `active_generation.json` pointer); promotion is atomic pointer swap. Rollback = restore the prior pointer (`data/lancedb_gold/.../active_generation.json`, `lexical_index_state`, corpus manifest). Retain the prior generation through the M8 rollback window.
4. **Manifest/pointer rollback:** `active_data_snapshot.json`, `b2o_working_db_path.txt`, corpus/index/source/probe/postbuild identity IDs are the pointers; M3 promotes new pointers, M8 retires old ones. Every report records the exact pointer set so a baseline run can be replayed.

Do not commit large generated DB/index/embedding artifacts (repository policy: `.gitignore` excludes them). Commit only manifests, reports, and reproducible commands.
