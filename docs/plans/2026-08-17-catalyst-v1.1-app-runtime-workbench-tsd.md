# Catalyst V1.1 Phase 5 Application Runtime + Workbench TSD

This document is a Phase 5 implementation design for the current repository. It is documentation only: it does not implement production code, modify Frozen V1.1, redesign Phases 2–4, or produce the final integrated TSD.

The normative baseline is docs/plans/2026-08-16-catalyst-vnext-frozen-v1-design.md. The factual baseline is docs/plans/2026-08-17-catalyst-v1.1-repo-reality-audit.md. Phase dependencies are docs/plans/2026-08-17-catalyst-v1.1-data-core-database-tsd.md, docs/plans/2026-08-17-catalyst-v1.1-agents-foundation-context-tsd.md, and docs/plans/2026-08-17-catalyst-v1.1-analyst-claims-corrective-tsd.md.

Repository evidence below names the relevant file, module, function, table, or frontend caller. Design decisions are labeled as target contracts and do not claim that the target already exists.

## 1. Executive Technical Assessment

The current application is a FastAPI process with SQLite-backed run/trace persistence and a React/Vite Workbench. The production entrypoint is packages/app/catalyst_app/main.py:create_app, which includes packages/app/catalyst_app/routers/live_runs.py and packages/app/catalyst_app/routers/workbench.py.

The current default path is durable only through run-row insertion. packages/app/catalyst_app/routers/live_runs.py:create_live_run starts one daemon thread per accepted request, packages/agents/catalyst_agents/runtime/service.py:LiveRunService creates a LiveRunRunner, and packages/agents/catalyst_agents/runtime/runner.py:LiveRunRunner invokes the graph. The current frontend caller is apps/workbench/src/components/workbench/LiveWorkbench.tsx:handleRun followed by its inline two-second status poll.

The migration is feasible without Redis, Celery, Kafka, Temporal, WebSockets, distributed workers, or a framework rewrite:

| Area | Assessment | Evidence / implication |
|---|---|---|
| Single-process bounded execution | FEASIBLE | The current Python/FastAPI process already owns admission and execution through LiveRunService and LiveRunRunner; replace per-request daemon threads with a process-owned bounded executor. |
| SQLite run/event/artifact persistence | SUFFICIENT FOR V1.1 | packages/agents/catalyst_agents/trace/schema.py already enables WAL, busy_timeout, primary-key event sequencing, artifacts, run links, and assurance rows. The event schema must be extended and writes made atomic. |
| Durable replay | FEASIBLE AFTER EVENT CONTRACT | GET /api/live-runs/{run_id}/events already reads ordered trace_events; SSE can tail the same persisted source with a process-local wakeup condition. |
| Honest cancellation | COOPERATIVE ONLY | packages/agents/catalyst_agents/runtime/runner.py uses future.cancel() and ThreadPoolExecutor, which cannot interrupt a running Python thread or an arbitrary provider request. Cancellation must be a persisted request plus boundary checks and result discard. |
| Real Writer streaming | FEASIBLE AFTER PHASE 4 WRITER | packages/app/catalyst_app/llm_factory.py returns ChatOpenAI, but no production stream callback exists. Phase 5 should bridge the Phase 4 StreamingWriter callback into coalesced persisted answer.delta events. |
| Frontend migration | FEASIBLE WITHOUT MAJOR REWRITE | apps/workbench/src/components/workbench/LiveWorkbench.tsx already has run controls, session data, evidence, stages, result tabs, and an API client. Replace its inline polling with one SSE reducer and retain existing visual components. |
| Claim/evidence navigation | FEASIBLE AFTER PHASE 4 ARTIFACTS | The frozen contract requires exact ValidatedClaimPlan IDs. The current workspace projection is Judge/Validator-shaped, so only the projection and detail APIs change; attribution semantics remain agent-owned. |

The most important target boundary is app-owned transport/runtime versus agents-owned semantic execution. Frozen V1.1 section 4.2 assigns HTTP admission, background execution, SSE, cancellation, credentials, and Workbench projection to packages/app; packages/agents remains the owner of RunManifest, trace, assurance, research, claims, Writer, and attribution status.

The most important current defects are:

1. packages/app/catalyst_app/routers/live_runs.py:create_live_run creates an unbounded-in-practice daemon thread per request.
2. packages/agents/catalyst_agents/runtime/service.py:run_next selects QUEUED rows without an atomic claim.
3. packages/agents/catalyst_agents/runtime/runner.py:_mark_running does not verify that the conditional QUEUED-to-RUNNING update succeeded before invoking the graph.
4. packages/agents/catalyst_agents/trace/writer.py:TraceWriter.event allocates event_seq in memory and commits the event before packages/agents/catalyst_agents/trace/artifacts.py:write_node_artifact commits artifacts separately.
5. packages/app/catalyst_app/routers/live_runs.py exposes event polling but no text/event-stream route.
6. apps/workbench/src/components/workbench/LiveWorkbench.tsx does not consume the existing event-polling hook or getLiveRunEvents; it fetches the final workspace only after a terminal status.
7. packages/app/catalyst_app/schemas.py mixes lifecycle states, epistemic statuses, and legacy internal trace statuses in one API surface.
8. packages/agents/catalyst_agents/runtime/dependencies.py:_load_once shares one read-only SQLite connection inside a cached ProductionHybridRetriever, which must be load-tested before allowing concurrent runs.

The target is a small, explicit runtime layer: durable admission, a bounded in-process executor, one SQLite event envelope, atomic artifact/event publication, SSE replay, cooperative cancellation, and a frontend reducer that reconstructs state from persisted events and artifacts.

### 4.2 API overlap and leakage

The current API has three overlapping progress surfaces: GET /api/live-runs/{run_id}, GET /events with after_seq, and GET /workspace. The first exposes node names and predicted_next_node; the second exposes trace rows and internal status names; the third exposes a v4 workspace projection built from Judge/Validator artifacts. The relevant implementation is packages/app/catalyst_app/routers/live_runs.py plus packages/app/catalyst_app/workspace_projection.py.

The target public contract keeps only domain DTOs. Internal graph node names, raw LangGraph state, Critic/Judge/Validator internals, raw provider responses, and free-form reasoning are not stable API fields. GET /events remains a compatibility endpoint only; its response should be the same public event DTO used by SSE rather than raw trace rows.

The current API has no Idempotency-Key handling, no stream URL, no claim/evidence detail route, no capability contract, no event heartbeat, and no explicit terminal event response. Those are additions to packages/app, not changes to Phase 2–4 domain ownership.

## 5. Runtime Execution Audit

### 5.1 Current primitives

| Concern | Current implementation | Consequence |
|---|---|---|
| Per-run thread | packages/app/catalyst_app/routers/live_runs.py:create_live_run and retry_live_run call threading.Thread(..., daemon=True).start(). | No global concurrency bound; repeated POSTs create repeated threads. |
| Inner executor | packages/agents/catalyst_agents/runtime/runner.py:LiveRunRunner.run creates ThreadPoolExecutor(max_workers=self.max_workers), default max_workers=1, for each run. | One outer daemon thread plus one inner worker per run; max_workers is per run, not process-wide. |
| Queue | packages/agents/catalyst_agents/runtime/service.py:run_next queries QUEUED rows; the API path does not use it. | No bounded queue and no backpressure response. |
| Queue claim | packages/agents/catalyst_agents/runtime/service.py:run_next selects then closes the connection; packages/agents/catalyst_agents/runtime/runner.py:_mark_running conditionally updates status. | Selection and claim are separate; two service workers could select the same run. |
| Run lock | No process-wide run/admission lock exists in packages/app/catalyst_app or packages/agents/catalyst_agents/runtime. | Duplicate active requests and task ownership are not coordinated. |
| Credential lock | packages/app/catalyst_app/runtime_credential_store.py uses threading.Lock around an in-memory dict. | Credential storage is thread-safe, but only one process and one run_id mapping are supported. |
| DB lock | packages/agents/catalyst_agents/trace/schema.py:init_trace_db enables WAL and busy_timeout=5000. | SQLite can serialize short writes; long or overlapping writes still need explicit transaction boundaries. |
| Shutdown | No FastAPI lifespan shutdown handler exists in packages/app/catalyst_app/main.py. | Executor/task cancellation and connection cleanup are not centrally coordinated. |
| Exception propagation | LiveRunRunner catches graph exceptions and updates agent_runs; graph TraceWriter may persist assurance, then the runner marks system error. | Current result/trace/run status ownership can diverge on late or duplicate terminal writes. |
| Cancellation | packages/agents/catalyst_agents/runtime/service.py:cancel_run updates agent_runs to CANCELLED; runner/provider work is not interrupted. | A run can be shown cancelled while the graph continues and writes artifacts. |
| Timeout | LiveRunRunner.run uses DEFAULT_TIMEOUT_SECONDS=300 and future.result(timeout=...). | future.cancel() cannot stop a running thread; stage/provider timeout settings also exist separately in packages/app/catalyst_app/llm_factory.py and RuntimeDependencyLoader. |

### 5.2 Atomic claiming

Current claiming is not atomic in packages/agents/catalyst_agents/runtime/service.py:run_next. The query SELECT run_id FROM agent_runs WHERE status = 'QUEUED' ORDER BY queued_at LIMIT 1 is followed by a close and a later runner call. packages/agents/catalyst_agents/runtime/runner.py:_mark_running uses UPDATE ... WHERE status = 'QUEUED', but LiveRunRunner.run does not inspect cursor.rowcount before loading state and invoking the graph.

The target does not need a distributed claim protocol. It needs one SQLite transaction in the app-owned admission/executor boundary:

1. Begin IMMEDIATE.
2. Select an eligible ACCEPTED/QUEUED row.
3. Update it to RUNNING with executor_owner and task_token, conditioned on the previous state.
4. Require rowcount=1.
5. Commit before graph invocation.
6. If rowcount=0, do not invoke the graph.

The same conditional-transition helper must be used for terminal state writes so a late timeout, cancellation, or graph result cannot overwrite a previously committed terminal state.

### 5.3 Failure and race matrix

| Scenario | Current behavior | Target behavior |
|---|---|---|
| Same request submitted twice | packages/agents/catalyst_agents/runtime/service.py:create_run always creates a new uuid4 run_id; no idempotency or active-request dedupe. | Same Idempotency-Key plus same request hash returns the original run; absent key uses normalized active-request dedupe. Different request under an existing key returns 409 IDEMPOTENCY_KEY_REUSED. |
| Queue is full | No queue bound exists; a new daemon thread starts. | Admission returns 429 RUN_CAPACITY_EXCEEDED without creating a run row, except a duplicate idempotent request returns its existing run. |
| Process exits before thread starts | The run may remain QUEUED with no durable task ownership; no startup recovery exists. | ACCEPTED/QUEUED rows are re-admitted at startup; never-running RUNNING rows are marked FAILED with PROCESS_RESTARTED or explicitly requeued only when no graph side effect began. |
| Process exits during graph | Daemon thread and in-memory credential disappear; SQLite may contain RUNNING and partial trace. | On next startup, RUNNING is terminalized as FAILED/PROCESS_RESTARTED with an integrity diagnostic; partial artifacts remain readable but cannot produce run.completed. |
| User cancels a queued run | service.cancel_run sets CANCELLED and ended_at immediately. | Conditional ACCEPTED/QUEUED → CANCELLED transaction, emit run.cancelled, release executor reservation if any. |
| User cancels during retrieval | DB status becomes CANCELLED, but retrieval may continue. | Persist CANCEL_REQUESTED, set control token, retrieval checks between task/arm boundaries, then discard any late result and commit CANCELLED. |
| User cancels during provider call | Current ChatOpenAI call continues; runner only observes status after future returns. | Call provider cancellation if supported; otherwise wait for return/timeout, discard output, and commit CANCELLED. Never claim hard interruption. |
| User cancels during Writer stream | No Writer stream exists today. | Stop accepting further deltas at the boundary; if provider cannot abort, continue draining/discarding safely, then emit run.cancelled with provisional invalidation if any delta was persisted. |
| Writer fails before first delta | Not currently represented. | One same-input technical retry allowed by Phase 4; if exhausted, run.failed WRITER_FAILURE with no provisional answer. |
| Writer fails after deltas | Not currently represented. | Persist assurance/invalidation metadata and run.failed; frontend marks provisional answer invalid, with no rewritten replacement. |
| Artifact write fails | packages/agents/catalyst_agents/graph.py:_trace_node swallows artifact exceptions after event commit. | Event and artifact publication are one transaction; failure is a run/system failure when artifact is required for correctness, not a silent observability loss. |
| Graph throws | runner marks FAILED_SYSTEM; TraceWriter may also finalize SYSTEM_ERROR. | One terminal-transition helper wins atomically; run.failed event carries typed stage/error code and artifact refs. |
| API client disconnects from SSE | No SSE exists; polling simply stops. | Disconnect closes only the HTTP generator. The run and event persistence continue; reconnect uses Last-Event-ID or persisted cursor. |
| DB write fails | SQLite exception can escape event/artifact/runner paths with partial writes. | Short transaction retries only for SQLITE_BUSY/locked within a bounded budget; otherwise typed DATABASE_FAILURE and no false terminal success. |

## 6. Run Admission

### 6.1 Target request and identity

The target API keeps the current /api/live-runs path to avoid a parallel /api/runs compatibility surface. The request DTO is a versioned app projection, not an agents domain object:

| Field | Contract |
|---|---|
| ticker | Trimmed uppercase target ticker. |
| trade_date | ISO calendar date. |
| query | Trimmed optional query, bounded to the existing 500-character validation ceiling unless a Phase 4 contract changes it. |
| model | Provider, model_id, base_url, credential_source; api_key is accepted only in memory and excluded from the identity hash. |
| config | Semantic workflow version/config name, defaulting to the current compatibility value during migration. |
| idempotency key | Optional HTTP Idempotency-Key header, bounded and treated as opaque. |

The normalized request identity is the SHA-256 of canonical JSON containing ticker, trade_date, normalized query or null, model provider, model_id, normalized base_url, credential_source, and config. It excludes api_key and any secret-bearing field. The implementation home is packages/app/catalyst_app/runtime/admission.py; the DTO projection remains in packages/app/catalyst_app/schemas.py.

### 6.2 Idempotency semantics

The current agent_runs table has no request hash or idempotency key. The target migration adds request_hash, idempotency_key, admission schema version, and optionally a request payload digest to agent_runs, with indexes:

| Lookup | Semantics |
|---|---|
| Existing idempotency_key with same request_hash | Return the original run_id and current status. Do not enqueue a second task. This applies to queued, running, completed, failed, and cancelled runs. |
| Existing idempotency_key with different request_hash | Return HTTP 409 with IDEMPOTENCY_KEY_REUSED. Do not reveal credentials or raw request payload. |
| No idempotency key and same request_hash in ACCEPTED/QUEUED/RUNNING/CANCEL_REQUESTED | Return the existing active run to protect against double-clicks and repeated browser submissions. |
| No idempotency key and no active match | Create a new run. Separate deliberate retries remain new run IDs through /retry. |
| Same normalized request after a terminal run without an idempotency key | Create a new run; the active-request dedupe is not a historical cache. |

A partial unique index on active request_hash and a unique index on idempotency_key are sufficient for one-process SQLite. The transaction must still use BEGIN IMMEDIATE and re-check both constraints because a process-local dictionary is not durable.

### 6.3 Admission transaction

The app-owned packages/app/catalyst_app/runtime/admission.py:RunAdmissionService performs:

1. Validate and normalize request fields using the existing packages/agents/catalyst_agents/runtime/validation.py policy or an app adapter that calls it without duplicating rules.
2. Resolve provider capability eligibility without persisting api_key.
3. Enter the single-process admission lock and BEGIN IMMEDIATE on the runtime DB.
4. Check idempotency_key and active normalized request_hash.
5. Reserve one bounded-executor capacity token.
6. Generate run_id, trace_id, request_hash, and RunManifest identity.
7. Insert agent_runs with status ACCEPTED, queued_at, request_hash, and model metadata only.
8. Append run.accepted as sequence 1 in the same transaction.
9. Commit.
10. Submit a task to the bounded executor. If submission fails after commit, transition ACCEPTED to FAILED with ADMISSION_SUBMISSION_FAILED and emit run.failed; do not leave a permanently accepted orphan.

The immediate response is:

{
  "run_id": "...",
  "status": "ACCEPTED",
  "stream_url": "/api/live-runs/{run_id}/stream"
}

The route returns as soon as the row and run.accepted event are durable. It does not wait for context construction, retrieval, a model call, or finalization.

### 6.4 Rejection conditions

| Condition | HTTP / status | Durable run row? |
|---|---|---|
| Malformed JSON or Pydantic request | 422 INVALID_REQUEST | No. |
| Unsupported ticker/date/no OHLCV session | 400 INVALID_RUN_REQUEST / existing typed sub_reason | Yes only if preserving the current FAILED_REQUEST audit behavior; target may return 400 without a run row for pure admission validation, but this must be one consistent contract. |
| Missing server-env credential | 400 MODEL_CREDENTIAL_UNAVAILABLE | No. |
| Model lacks required Writer streaming/structured capability | 409 MODEL_CAPABILITY_UNAVAILABLE | No. |
| Runtime identity health failed | 503 DATA_RUNTIME_UNAVAILABLE | No, unless the operator wants a durable rejected admission record. |
| Executor capacity exhausted | 429 RUN_CAPACITY_EXCEEDED with Retry-After | No. |
| Idempotency key reused for different request | 409 IDEMPOTENCY_KEY_REUSED | Existing original row remains unchanged. |
| SQLite busy beyond bounded admission retry | 503 ADMISSION_STORAGE_BUSY | No new row. |

The target should not preserve the current practice of returning HTTP 200 with status FAILED_REQUEST for all provider/admission failures. Compatibility parsing can continue to understand old response rows.

## 7. Bounded Executor

### 7.1 Choice

Use the Python standard-library concurrent.futures.ThreadPoolExecutor behind an app-owned bounded admission wrapper. Do not use asyncio tasks as the primary graph executor because the current graph, retrieval adapters, LangChain provider calls, LanceDB access, and embedding/reranker code are synchronous.

The implementation homes are packages/app/catalyst_app/runtime/executor.py and packages/app/catalyst_app/runtime/service.py. packages/agents/catalyst_agents/runtime/runner.py should become the graph execution adapter and must not create an executor per run.

### 7.2 Capacity contract

Initial configuration:

| Parameter | Initial target | Owner |
|---|---:|---|
| max_workers | 2 | app runtime config; load test may pin 2–4 as Frozen V1.1 requires. |
| max_pending | 4 | app runtime config; includes ACCEPTED/QUEUED tasks with reserved capacity. |
| total admission capacity | 6 | executor wrapper, not ThreadPoolExecutor's unbounded internal queue. |
| task timeout | RunManifest deadline, initial 60 seconds per Frozen V1.1 | agents RunManifest plus app enforcement. |
| event write retry | Small bounded retry for SQLITE_BUSY only | event repository. |
| SSE heartbeat | 10 seconds, non-persisted comment | SSE endpoint. |

The wrapper uses a BoundedSemaphore(max_workers + max_pending) or equivalent explicit capacity counter. It calls ThreadPoolExecutor.submit only after capacity reservation and releases the token in a done callback. A bare ThreadPoolExecutor is insufficient because its internal work queue is unbounded.

The exact max_workers value is a load-test parameter, not an unresolved architectural choice. The final integration must test 2, 3, and 4 concurrent runs against the actual SQLite connection, reranker, embedding model, provider SDK, and artifact write load.

### 7.3 Task bookkeeping

The app-owned executor tracks run_id → Future, task token, admitted_at, and owner process identifier in memory. Durable ownership remains in agent_runs.executor_owner/task_token and status. The in-memory map is an optimization for cancellation and shutdown, not the source of truth.

The executor must:

- reject submission when no capacity token is available;
- release capacity exactly once through Future completion;
- capture exceptions and pass them to the lifecycle service;
- avoid logging credentials or full provider exceptions;
- expose active and pending counts through /api/health;
- support a shutdown(cancel_pending=True) operation through FastAPI lifespan;
- stop accepting new runs before shutdown;
- transition admitted but unstarted rows to FAILED with PROCESS_SHUTDOWN or requeue them on explicit restart recovery.

### 7.4 Shared dependency safety

packages/agents/catalyst_agents/runtime/dependencies.py:_load_once caches RuntimeDependencies, including a single check_same_thread=False SQLite connection inside ProductionHybridRetriever. Before raising concurrency above one, Phase 5 implementation must either construct a per-run/per-thread read connection in packages/data-core/catalyst_data/retrieval/hybrid.py or serialize access around the shared connection. LanceDB table reads and the reranker must also be load-tested for concurrent calls.

This is a concrete integration dependency, not a reason to add external workers.

## 8. Run Lifecycle Persistence

### 8.1 Lifecycle versus semantic result

The current packages/app/catalyst_app/schemas.py:RunStatus and packages/agents/catalyst_agents/runtime/status.py normalize_run_status mix lifecycle and epistemic values. The target separates:

- run lifecycle: ACCEPTED, QUEUED, RUNNING, CANCEL_REQUESTED, COMPLETED, FAILED, CANCELLED;
- result_status: SUCCEEDED, PARTIAL, ABSTAIN, or null until a valid result is assured;
- failure_code: typed technical/system reason or null;
- internal semantic stage: owned by Phase 4 artifacts and RunManifest, not duplicated in the app lifecycle table.

ABSTAIN and PARTIAL are not run failures. A valid ABSTAIN or PARTIAL result reaches COMPLETED with result_status set. A model timeout, assurance failure, database failure, or invalidation reaches FAILED. CANCELLED is a runtime control terminal state and does not synthesize an epistemic answer.

### 8.2 State machine

| From | To | Authority / condition |
|---|---|---|
| ACCEPTED | QUEUED | Executor accepts the durable task and records queue ownership. |
| ACCEPTED | RUNNING | Allowed only if the executor claims directly; conditional row update required. |
| ACCEPTED | CANCELLED | Queued cancellation before graph start. |
| ACCEPTED | FAILED | Admission submission failure or process recovery failure. |
| QUEUED | RUNNING | Atomic executor claim with status=QUEUED and owner token. |
| QUEUED | CANCEL_REQUESTED | Cancel request races with a queued task and cannot immediately guarantee worker state. |
| QUEUED | CANCELLED | Worker observes cancellation before graph start; emit terminal run.cancelled. |
| QUEUED | FAILED | Storage, startup recovery, or submission failure. |
| RUNNING | CANCEL_REQUESTED | API cancellation request accepted; control token set. |
| RUNNING | COMPLETED | Final assured result committed atomically with run.completed. |
| RUNNING | FAILED | Typed technical/integrity failure committed with run.failed. |
| RUNNING | CANCELLED | Cooperative cancellation acknowledged at a safe boundary; emit run.cancelled. |
| CANCEL_REQUESTED | CANCELLED | Cancellation boundary reached or provider call output discarded. |
| CANCEL_REQUESTED | FAILED | Cancellation handling itself encounters an integrity/storage failure; no result is published. |
| COMPLETED / FAILED / CANCELLED | none | Terminal. /retry creates a new run row and run_links relation; it does not reopen the old row. |

The status update and terminal event must be one transaction with a conditional WHERE status IN (...). A late graph completion after timeout/cancellation has rowcount=0 and its result is discarded. If it wrote non-terminal diagnostic artifacts before the terminal transition, those artifacts remain marked provisional/incomplete and cannot be referenced as an assured result.

### 8.3 Target run-row envelope

Evolve agent_runs rather than creating a parallel lifecycle table:

- run_id, trace_id;
- lifecycle_status;
- result_status;
- ticker, trade_date;
- queued_at, started_at, ended_at;
- request_hash, idempotency_key;
- config/workflow version;
- RunManifest artifact_id and manifest hash;
- executor_owner/task_token;
- deadline_at;
- failure_code/failure_message_digest;
- total latency, tokens, cost;
- retention_class.

The existing status/config/error columns in packages/agents/catalyst_agents/trace/schema.py remain readable during migration. A compatibility projection maps old SUFFICIENT/SYSTEM_ERROR/FAILED_SYSTEM values into lifecycle/result DTOs; new writes use the separated fields.

## 9. Cancellation

### 9.1 Ownership and control token

packages/app/catalyst_app/runtime/cancellation.py owns cancellation requests, persisted state transitions, and the process-local control registry. packages/agents/catalyst_agents/runtime/control.py should define the narrow agent-side protocol for should_cancel(), deadline(), and cancellation_reason() without importing packages/app.

The app passes an implementation of that protocol into the agents execution adapter. The agent graph, Phase 3 retrieval executor, Phase 4 Evidence Analyst adapter, ClaimValidator, and StreamingWriter observe it at boundaries. The app does not own semantic retry, evidence state, or claim decisions.

### 9.2 Semantics by stage

| Stage | Cancellation behavior |
|---|---|
| ACCEPTED/QUEUED before graph | Conditional terminal cancellation; no semantic stage starts. |
| Observation/context | Check before and after the stage; if requested, do not publish the next stage artifact. |
| Initial retrieval | Check before each bounded task/arm and after each result. Optional task results may be discarded; required cancellation ends the run. |
| Analyst model request | Attempt provider cancellation only if the adapter exposes it. Otherwise wait for the provider call to return or timeout, discard the response, and commit CANCELLED. |
| Corrective retrieval | Same boundary rules as initial retrieval; no new corrective action is started after request. |
| Writer before first delta | Stop before publishing; retry is not initiated after cancellation. |
| Writer after deltas | Stop publishing new deltas; if the provider cannot abort, drain/discard; mark provisional output invalid and emit run.cancelled. |
| SSE | Disconnect has no cancellation effect. Only POST /cancel requests cancellation. |

The API returns 202 with status CANCEL_REQUESTED when a RUNNING call cannot yet be interrupted. It returns 200 with CANCELLED when the transition is already committed. A second cancel is idempotent. A cancel arriving after COMPLETED/FAILED returns the terminal state and does not rewrite it.

### 9.3 No false hard interruption

Python ThreadPoolExecutor.future.cancel() returns false for a running task and does not stop provider I/O. packages/agents/catalyst_agents/runtime/runner.py currently relies on that behavior. The target uses it only to prevent queued work from starting; it never claims to kill a running graph or provider call.

A non-cancellable in-flight provider result must not complete a cancelled run. The lifecycle service checks the conditional terminal transition before publishing result artifacts/events. If the row is already CANCEL_REQUESTED/CANCELLED, the result is discarded.

## 10. Timeout Semantics

### 10.1 One run deadline

The canonical deadline is stored in the Phase 4 RunManifest artifact and copied into agent_runs.deadline_at. Frozen V1.1 initially targets a 60-second run-level timeout with narrower stage budgets. The current packages/agents/catalyst_agents/runtime/runner.py DEFAULT_TIMEOUT_SECONDS=300 and packages/app/catalyst_app/llm_factory.py ChatOpenAI timeout=90 are migration inputs, not the final contract.

The app owns the outer watchdog and terminal lifecycle transition. Agents own stage budget checks and typed model/retrieval error classification. There must be one effective minimum deadline:

effective_stage_deadline = min(run_deadline, stage_budget_deadline, provider_timeout_deadline)

A stage timeout maps to a technical failure such as MODEL_TIMEOUT, RETRIEVAL_TIMEOUT, or WRITER_TIMEOUT. It never maps to epistemic ABSTAIN.

### 10.2 Timeout layers

| Layer | Owner | Target behavior |
|---|---|---|
| Run-level deadline | app executor plus RunManifest | At deadline, set control timeout, conditionally transition RUNNING/CANCEL_REQUESTED to FAILED with RUN_TIMEOUT, and publish run.failed. |
| Observation/retrieval task budget | agents Phase 3 executor | Stop starting new tasks after deadline; preserve per-task degradation only if the Phase 3 policy allows a valid degraded result. |
| Analyst/Writer provider timeout | agents provider adapter using capability contract | Normalize to MODEL_TIMEOUT/WRITER_TIMEOUT; one technical retry only where Phase 4 allows. |
| SSE connection | app SSE generator | Heartbeat every 10 seconds; client disconnect does not stop the run; no run-level deadline extension. |
| Shutdown | app lifespan | Stop admission, request cancellation for active runs, wait a bounded grace period, then mark unresolved RUNNING rows PROCESS_SHUTDOWN on next startup. |

A timeout after any answer.delta invalidates provisional rendering and emits run.failed with provisional_output_invalidated=true. A timeout before deltas emits only the technical failure path.

## 12. Event Sequencing / Transactions

### 12.1 Sequence allocation

The current packages/agents/catalyst_agents/trace/writer.py:TraceWriter._event_seq is process-local and resets on each writer. It is not sufficient for replay after restart or concurrent delta publication.

The target packages/app/catalyst_app/runtime/event_store.py:EventRepository.append opens a short SQLite transaction with BEGIN IMMEDIATE, computes max(event_seq)+1 for the run, inserts the event row, inserts any artifact rows, and commits. The sequence is allocated from the database, not from an in-memory counter.

The existing PRIMARY KEY(run_id,event_seq) in packages/agents/catalyst_agents/trace/schema.py remains the uniqueness guard. A sequence collision retries the append once after re-reading max(seq); repeated collision is EVENT_SEQUENCE_FAILURE. SQLite's single-writer serialization makes MAX(seq)+1 safe when the transaction begins IMMEDIATE. A separate counter table is unnecessary for the single-process V1.1 target.

### 12.2 Atomic publication

Required transaction patterns:

| Operation | Transaction |
|---|---|
| Admission | Insert/lookup run identity, run.accepted event, RunManifest/admission artifact ref, and initial lifecycle status in one transaction. |
| Stage start | Insert stage.started and any stage input artifact refs in one transaction. |
| Retrieval/assessment completion | Insert completed artifact first or within the same transaction, then the event referencing it; commit once. |
| Writer delta | Insert one answer.delta event per coalesced chunk; no large artifact required. |
| Answer completion | Insert final Answer/provisional artifact and answer.completed event in one transaction. |
| Assurance/terminal | Insert Assurance artifact, update agent_runs lifecycle/result fields, and insert assurance.completed plus run.completed/run.failed in one transaction. |
| Cancellation | Update lifecycle to CANCEL_REQUESTED or CANCELLED and emit the corresponding terminal event in one transaction. |

packages/agents/catalyst_agents/graph.py:_trace_node currently commits an event before packages/agents/catalyst_agents/trace/artifacts.py:write_node_artifact and swallows artifact failure. That behavior must not remain for required Phase 2–4 artifacts. Observability-only debug artifacts may be best-effort, but their event must declare that they are optional and cannot be used as authoritative Workbench data.

### 12.3 Legacy trace compatibility

Existing trace_events rows have node-oriented fields and no public event_type/payload/artifact_refs columns. The migration adds nullable/versioned public columns and backfills old rows as legacy stage events only when their meaning is known. Old API consumers continue to receive compatibility projections. New V1.1 writes never depend on an in-memory sequence or on raw node names for frontend behavior.

## 13. SSE Contract

### 13.1 Endpoint and framing

Target endpoint: GET /api/live-runs/{run_id}/stream in packages/app/catalyst_app/routers/live_runs.py.

Response:

- HTTP 200;
- Content-Type: text/event-stream; charset=utf-8;
- Cache-Control: no-cache;
- X-Accel-Buffering: no;
- connection kept open until terminal event, explicit not-found, or client disconnect.

Each persisted event is framed:

id: {run_id}:{sequence}
event: {event_type}
data: {single-line JSON envelope}

The data JSON contains schema_version, run_id, sequence, emitted_at, stage, payload, and artifact_refs. The id is the stable network identity. A heartbeat is a non-persisted comment frame every 10 seconds, for example : heartbeat; it has no sequence and is not replayed.

### 13.2 Headers and errors

| Condition | Response |
|---|---|
| Unknown run_id | 404 RUN_NOT_FOUND before streaming begins. |
| Malformed Last-Event-ID | 400 INVALID_EVENT_CURSOR. |
| Last-Event-ID for another run | 400 INVALID_EVENT_CURSOR; do not silently merge streams. |
| Runtime DB unavailable | 503 EVENT_STORE_UNAVAILABLE before streaming begins. |

## 14. Replay Algorithm

The replay algorithm must work after browser refresh, process restart, and a race between the initial query and live publication.

1. Parse Last-Event-ID. If absent, use cursor 0. If present, require format run_id:sequence and verify the run_id matches the path.
2. Look up the run. Return 404 if absent.
3. Acquire the process-local condition for run_id from packages/app/catalyst_app/runtime/event_store.py. The condition is only a wakeup optimization; SQLite remains the source of truth.
4. While streaming:
   1. Hold the condition lock.
   2. Query trace_events for run_id and event_seq > cursor ordered ASC.
   3. Query the run lifecycle/terminal event state in the same read view.
   4. If rows exist, release the lock, emit rows in order, and advance cursor only after each row is framed. The client may receive a duplicate on disconnect; this is intentional at-least-once delivery.
   5. If a terminal event was included, close after emitting it.
   6. If no rows and the run is already terminal, close. A terminal status is only considered complete when its terminal event is in the same transaction, so a status/event visibility gap cannot occur.
   7. If no rows and not terminal, call condition.wait(timeout=10). The timeout emits a non-persisted heartbeat and repeats.
5. EventRepository commits the event transaction before acquiring the same condition and notifying. If a writer commits between the reader query and wait, the reader holds the condition lock during the query; the writer blocks until wait atomically releases the lock and then notifies. This removes the replay-to-live lost-wakeup race.
6. If a process restarts, the in-memory condition is recreated, but the initial SQLite query replays all persisted events after Last-Event-ID before waiting.

The endpoint must never rely solely on an in-memory queue. The queue/condition is only a low-latency wakeup path; replay, ordering, and terminal detection are database-backed.

## 15. Delivery Semantics

The contract is at-least-once delivery, not exactly-once network delivery.

The stable deduplication key is (run_id, sequence). The frontend reducer in apps/workbench/src/state/run-event-reducer.ts must ignore an event whose sequence is already applied and must tolerate a gap by retaining the last applied sequence and reconnecting/replaying from it.

The server persists before emission. A client can receive an event, disconnect before committing its local cursor, and receive it again. The frontend must apply the event idempotently. A client must not infer semantic meaning from arrival count or network timing.

Event sequence is per run, not globally ordered across runs.

## 16. Writer Streaming Bridge

### 16.1 Ownership

Phase 4 owns StreamingWriter.stream(WriterInput) and provider deltas in packages/agents/catalyst_agents/nodes/writer.py. Phase 5 owns the transport bridge and persistence in packages/app/catalyst_app/runtime/streaming.py plus the event repository.

The provider delta path is:

provider stream chunk → Writer adapter normalization → bounded coalescer → EventRepository.append(answer.delta) → SSE condition notify → frontend reducer.

The app must not call the provider a second time or slice a completed answer into fake deltas. Delta content is accepted only from the provider streaming iterator/callback. A non-streaming provider is offline/test-only and cannot satisfy the production Writer capability.

### 16.2 Coalescing

Initial policy:

- flush at 50 milliseconds;
- flush at 2,048 UTF-8 characters, whichever comes first;
- flush immediately when the provider signals end-of-stream;
- persist one event per coalesced chunk, not one SQLite row per provider token;
- include delta_ordinal and cumulative_character_count;
- cap a single delta payload at the event limit.

This stays within Frozen V1.1's approximately 30–80 millisecond target and is perceptibly streaming. It also bounds SQLite write amplification at roughly 20 delta writes per second per active stream in the worst time-based case.

The coalescer must not buffer the full answer before the first event. It flushes independently of final answer completion. If the provider emits a very large chunk, split only that provider chunk into bounded transport chunks while retaining provider-origin metadata; do not generate deltas from the final answer after the fact.

### 16.3 Completion and usage

At provider completion:

1. finalize the exact accumulated text;
2. persist the Answer/provisional artifact with text hash, claim/citation IDs, and stream ID;
3. append answer.completed in the same transaction;
4. wait for Phase 4 assurance;
5. append assurance.completed and terminal event.

Token usage, model/provider, cost status, and retry count come from the provider adapter and RunManifest. If usage is unavailable, persist null/unknown rather than fabricate a number.

### 16.4 Backpressure

SSE clients do not receive direct provider callbacks. The writer only waits for short SQLite event commits; it never waits for a browser socket. A bounded per-run delta buffer protects the writer if SQLite is unavailable. If the buffer exceeds a configured limit, the run fails with STREAM_PERSISTENCE_BACKPRESSURE and any provisional output is invalidated.

## 17. Provisional Rendering / Assurance

The public lifecycle is:

1. answer.started: Writer begins; frontend shows provisional state.
2. answer.delta: frontend renders text with an explicit provisional/pending-assurance label.
3. answer.completed: full provisional text and citations are persisted, but the result is not yet assured.
4. assurance.completed: frontend receives valid=true or valid=false with bounded violations.
5. run.completed: only valid assured output reaches terminal completion.
6. run.failed: assurance failure, Writer failure, timeout, cancellation after output, or other technical/integrity error.

If assurance fails after answer.completed:

- assurance.completed has valid=false;
- run.failed has failure_code=ASSURANCE_FAILED;
- payload includes provisional_output_invalidated=true;
- frontend replaces the provisional answer with an explicit invalidated/failure state;
- no silent rewritten answer is emitted;
- no second semantic or Writer call is introduced by app transport.

A valid epistemic ABSTAIN follows the same Writer and assurance path as a causal answer. It is displayed as a completed bounded result, not as a technical error.

## 19. Event vs Artifact Boundary

Events contain:

- lifecycle event type;
- stage and round/task identifiers;
- compact candidate/selected/accepted ID lists within a bounded payload;
- counts, latency, degradation codes, usage summaries;
- artifact references, hashes, and schema versions;
- provisional/invalidated flags.

Artifacts contain:

- full structured Phase 2–4 objects;
- bounded evidence arrays and excerpts;
- ContextPack exact excerpts/offsets;
- claim/citation maps;
- WriterInput/Answer;
- assurance details;
- RunManifest identity.

The frontend receives events first for progress and then fetches artifacts on demand or when the event references an artifact needed by the current panel. It never reconstructs causal relations from titles, snippets, ranks, or node order. The backend projection is authoritative.

Initial operational limits:

| Object | Initial limit | Handling |
|---|---:|---|
| Public event payload | 64 KiB | Move large content to artifact; reject if compact payload itself is oversized. |
| Answer delta | 2,048 UTF-8 characters before coalescer split | Persist provider-derived chunks only. |
| Evidence detail excerpt | Phase 2/3 bounded excerpt contract | Never expose full raw provider payload by default. |
| Structured artifact JSON | 25 MiB default, configurable | Fail closed for required artifacts; debug artifacts may be omitted with a degradation code. |
| API response page | 100 evidence/artifact items default | Use IDs/detail endpoints and pagination rather than one huge workspace response. |

## 31. Reconnect / Refresh

### 31.1 Browser refresh during run

On app mount:

1. Read the current run_id and last_event_seq from sessionStorage/localStorage or a URL state chosen by the frontend contract.
2. Fetch GET /api/live-runs/{run_id}.
3. Fetch the current workspace/artifact refs if the summary contains them.
4. Open SSE with Last-Event-ID run_id:last_event_seq.
5. Reduce replayed events idempotently.
6. Fetch artifact detail for events that reference new artifacts.
7. Continue until terminal event, then persist final cursor and terminal projection.

The frontend must not require an in-memory JavaScript session to reconstruct a run.

### 31.2 Disconnect/sleep/reconnect

On EventSource error or fetch-stream disconnect:

- mark connection_state=reconnecting;
- retain the last applied sequence;
- use bounded exponential backoff;
- reconnect with Last-Event-ID;
- do not reset the result or duplicate evidence;
- if the run is terminal, replay and close rather than waiting indefinitely.

Duplicate event delivery is expected. A sequence gap is a reconnect trigger, not a semantic error. If a gap persists, the client fetches GET /events?after_seq=last_event_seq as a compatibility repair path.

### 31.3 Writer-specific reconnect

If the browser reconnects after answer.completed but before assurance.completed, it replays answer events and then assurance/terminal events. The answer remains visibly provisional until assurance.completed. If run.failed invalidates it, the reducer removes it from the assured result view and displays the invalidation state.

- bounded worker count never exceeds configured max;
- pending capacity never exceeds configured bound;
- atomic claim allows only one executor to start a run;
- transition rowcount prevents cancelled/terminal rows from invoking graph;
- completion writes lifecycle/result status and run.completed atomically;
- graph exception emits run.failed once;
- timeout prevents late graph result from completing the run;
- shutdown recovery terminalizes or requeues rows according to policy;
- task exceptions release capacity exactly once.

### 34.3 Event persistence

- sequence starts at one and is monotonic;
- two concurrent appenders for one run cannot duplicate sequence;
- sequence resumes after process/writer recreation;
- run.accepted and run row are same transaction;
- artifact refs never point to a missing artifact;
- artifact write failure prevents a falsely published required event;
- event payload limit is enforced;
- safe payload redaction excludes credentials/raw responses.

### 34.4 SSE

- content type and required headers;
- replay from no Last-Event-ID;
- replay from run_id:sequence;
- malformed/mismatched cursor;
- events arrive ordered;
- terminal event closes stream;
- heartbeat is a non-persisted comment;
- writer publication wakes live tail;
- replay/live race does not lose an event;
- disconnect leaves run execution intact;
- reconnect receives duplicates safely;
- at-least-once identity is run_id/sequence.

### 34.5 Cancellation/timeout

- queued cancellation is immediate terminal;
- running cancellation returns CANCEL_REQUESTED then CANCELLED;
- cancellation during a non-cancellable fake provider discards late result;
- provider cancellation hook is called when supported;
- cancellation after terminal is idempotent/no-op;
- timeout before delta emits technical run.failed;
- timeout after delta invalidates provisional output;
- ABSTAIN/PARTIAL remain COMPLETED, not FAILED.

### 34.6 Artifact/detail APIs

- artifact lookup returns same-run artifact;
- foreign/unknown artifact ID returns 404;
- evidence detail resolves canonical fields and bounded excerpt;
- claim detail returns exact support/counter IDs;
- claim endpoint does not infer links from frontend input;
- large artifact pagination/ref behavior;
- evaluator/permanent artifacts survive cleanup.

Use a deterministic fake run producer that emits the public event sequence and Phase 2–4 fixture artifacts. It should not require external LLM, LanceDB, or a real browser.

## 36. Performance / Backpressure

### 36.1 Practical limits

The current target is a local Workbench, not cloud-scale multi-tenant infrastructure.

| Resource | Initial design envelope | Protection |
|---|---:|---|
| Concurrent graph runs | 2 initially; test up to 4 | Bounded executor and capacity reservation. |
| Pending runs | 4 initially | Semaphore/capacity rejection with HTTP 429. |
| Writer event rate | Coalesced 50 ms / 2,048 chars | Per-chunk persistence, no per-token rows. |
| SSE clients | Local developer scale; no fixed cloud SLA | Each client reads persisted events; condition is a wakeup only. |
| Event DB writes | Short WAL transactions | Payload limits, bounded retries, no browser backpressure. |
| Artifact payload | 25 MiB default JSON envelope | Ref/detail APIs, bounded excerpts, fail-closed required artifacts. |
| Workspace response | Paged/ref-based after migration | Do not join all evidence/context into one response. |

The first performance gate is actual load testing with the promoted SQLite/database, RuntimeDependencyLoader, LanceDB table, BGE-M3 embedding, reranker, provider adapter, event delta rate, and two to four runs. The event stream should not use a network queue or in-memory full-run buffer.

### 36.2 SQLite considerations

packages/agents/catalyst_agents/trace/schema.py already enables WAL and busy_timeout. The target must keep transactions short, open independent connections for concurrent runtime operations, and avoid sharing the cached RuntimeDependencyLoader read connection unsafely. Event readers should use read-only connections; event writers should use a dedicated short-lived connection or a serialized event-store writer lock.

Do not add Redis/Kafka solely to avoid SQLite contention at this scale.

## 42. Final Feasibility Verdict

1. Can the current app migrate to managed bounded execution without external queue infrastructure? **Yes.** packages/app already owns the HTTP route and packages/agents already expose a synchronous graph invocation boundary. A process-wide ThreadPoolExecutor plus explicit semaphore capacity is sufficient for the local Workbench. The current per-run daemon-thread approach must be replaced.
2. Is SQLite sufficient for V1.1 run/event/artifact persistence? **Yes for the single-process target.** packages/agents/catalyst_agents/trace/schema.py already uses WAL, busy_timeout, event PKs, artifact tables, and assurance persistence. The main required change is atomic event/artifact publication and a durable DB-backed sequence, not a new database.
3. What is the safest monotonic event-sequence mechanism? **SQLite BEGIN IMMEDIATE plus MAX(event_seq)+1 inside the same insert transaction, protected by PRIMARY KEY(run_id,event_seq).** A run-local in-memory counter in TraceWriter is insufficient after restart.
4. Can real provider Writer streaming be persisted and replayed without excessive write amplification? **Yes.** Phase 4 provides the Writer boundary; a 30–80 ms/2,048-character coalescer persists provider-derived answer.delta chunks. SSE clients read persisted rows, so browser speed does not backpressure provider calls.
5. Can cancellation be implemented honestly with current providers? **Yes as cooperative cancellation, not hard interruption.** packages/agents/catalyst_agents/runtime/runner.py proves future.cancel() cannot stop a running thread. A cancellation token, provider hook where supported, boundary checks, and late-result discard meet the Frozen contract.
6. Can polling be removed cleanly? **Yes.** The default LiveWorkbench currently uses inline polling, while useLiveRunPolling.ts is a separate unused path. Replace the default with one SSE reducer, retain GET /events only as an explicitly temporary fallback, then remove both polling implementations.
7. Can the current frontend consume SSE without a major framework rewrite? **Yes.** React/Vite already has typed API wrappers, run state, workspace panels, and event-shaped types. Add a stream parser/hook and reducer; preserve the existing v4 component tree.
8. Can browser refresh reconstruct a running/completed Workbench? **Yes after durable events/artifacts and cursor persistence.** GET run, Last-Event-ID replay, artifact refs, and same-run claim/evidence APIs provide all required sources. The current default UI cannot do it because it only fetches workspace after terminal.
9. Are claim→evidence navigation and evidence details supported by Phase 4 artifacts? **They are supported by the target Phase 4 ValidatedClaimPlan/EvidenceState contracts, not by the current Judge/Validator workspace projection.** The app needs run-scoped claim/evidence detail projections and must not infer relations.
10. Is any Frozen V1.1 API/SSE contract unrealistic against the current repository? **No architectural requirement is unrealistic, but none is currently implemented end-to-end.** The concrete blockers are bounded executor migration, event schema evolution, true Writer streaming, provider capability proof, canonical artifact projections, and runtime identity configuration.
11. Which implementation details must be carried into final integration? **The lifecycle/result split; idempotent admission; atomic SQLite claim and terminal transitions; DB-backed sequence; artifact/event atomicity; Last-Event-ID replay race handling; cooperative cancellation/late discard; provisional assurance invalidation; provider capability admission; same reducer for SSE/fallback; loopback security; and shared retrieval-connection concurrency testing.**

The correct migration is a transport/runtime cutover around the existing package boundaries, not an infrastructure expansion and not a new attribution architecture.

## 43. Narrow Contract Clarifications

1. Keep /api/live-runs as the canonical V1.1 path. Do not introduce /api/runs as a parallel alias.
2. HTTP admission status is ACCEPTED. Persisted lifecycle status may transition through QUEUED, but the API must return after run.accepted is durable and before graph completion.
3. Separate lifecycle status from epistemic result_status. COMPLETED+ABSTAIN and COMPLETED+PARTIAL are valid results; FAILED is technical/integrity failure.
4. CANCEL_REQUESTED is an internal/persisted transitional state. The public terminal event remains run.cancelled.
5. Reuse trace_events as the canonical public event table after adding versioned event envelope fields; retain old node/timing columns for compatibility while Phase 4 projections migrate.
6. Keep node_artifacts as the Phase 3/4 artifact store and add an artifact envelope/ref/hash/index rather than creating one SQL table per domain artifact.
7. Event refs must be written in the same SQLite transaction as the referenced required artifact. A required artifact cannot be an eventually consistent side effect.
8. Last-Event-ID is run_id:sequence. Delivery is at least once; frontend dedupe uses run_id and sequence.
9. A 10-second heartbeat is a transport comment, not a persisted event and not part of sequence allocation.
10. Writer deltas are provider-derived and coalesced at approximately 50 ms/2,048 characters; answer.completed remains provisional until assurance.completed.
11. Assurance failure after deltas emits run.failed with provisional_output_invalidated=true; the app must not rewrite the answer.
12. The target runtime starts with two workers and four pending slots, then pins between two and four workers only after actual promoted-runtime load testing.
13. Provider capability probing is cached/preflight behavior, not an additional attribution model call; production Writer admission requires real streaming support.
14. GET /workspace remains a compatibility aggregate during migration, but authoritative Workbench panels consume versioned Phase 2–4 artifact projections rather than raw Judge/Validator fields.
15. Retention defaults to 30 days for normal run artifacts/events and permanent protection for versioned eval artifacts; no current cleanup implementation is assumed.
