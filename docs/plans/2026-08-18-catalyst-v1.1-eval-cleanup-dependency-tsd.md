## 1 Executive Technical Assessment
- The repository has a substantial offline evaluation surface, but it evaluates several incompatible contracts: `packages/eval/catalyst_eval/schema/golden_event.py:GoldenEvent`, `packages/eval/catalyst_eval/schema/result.py:AttributionResult`, `packages/eval/catalyst_eval/benchmark/case.py:BenchmarkCase`, and `packages/eval/catalyst_eval/post_import/case_pack.py:CasePackCase` are all active schema families.
- The only strict benchmark model is `packages/eval/catalyst_eval/benchmark/case.py:BenchmarkCase`; no checked-in dataset currently instantiates the Frozen V1.1 `GoldenCase` contract with cutoff, evidence judgments, expected attribution, and expected research behavior together.
- Current retrieval evaluation is stronger than current attribution and trajectory evaluation: `packages/eval/catalyst_eval/post_import/four_arm.py:run_four_arm` and `packages/eval/catalyst_eval/post_import/t4_evidence.py:validate_t4_evidence` bind runtime/index identity, while `packages/eval/catalyst_eval/metrics/*` still scores legacy result/golden schemas and uses LLM judges for important diagnostic metrics.
- Current T4 is a fail-closed runtime/index smoke contract, not a V1.1 human-labelled attribution benchmark. Its ten cases are assembled by `packages/eval/catalyst_eval/post_import/case_pack.py:build_smoke_case_pack` from older golden files and do not contain Frozen V1.1 evidence judgments or research-behavior labels.
- Current agent trajectory evaluation is not present as a human-grounded suite. `packages/eval/catalyst_eval/harness/three_arm.py` records legacy Arm A/B/C behavior, but it does not score the Frozen V1.1 A1–A5 contracts or bounded corrective behavior against human-labelled expected actions.
- The current test pyramid has useful unit and integration coverage across `packages/data-core/tests`, `packages/agents/tests`, `packages/app/tests`, and `packages/eval/tests`, but no repository-level CI workflow was found under `.github/`, and `apps/workbench/package.json` has no test script.
- Cleanup must be staged around reproducibility: legacy schemas, T4 artifacts, and the old frozen harness are required for baseline preservation until an identity-bound V1.1 result can be compared against them. They must not remain parallel production semantics after cutover.
- The critical dependency is evaluation-contract readiness, not metric implementation alone: the V1.1 `GoldenCase`, pinned `EvalManifest`, human labels, runtime identity, and case-pool provenance must exist before Stage-1 numbers can be interpreted.

## 6 GoldenCase V1.1

### Required case contract

The Frozen V1.1 `GoldenCase` fields are defined in `docs/plans/2026-08-16-catalyst-vnext-frozen-v1-design.md`. The following is the one canonical case contract. Dataset/version/lineage fields are envelope metadata, not alternate case semantics.

| Field | Type / allowed shape | Ground-truth authority |
|---|---|---|
| `case_id` | Opaque stable string | Human case registry; `BenchmarkCase.case_id` is the current precedent |
| `ticker` | Canonical uppercase string | `packages/data-core` identity policy |
| `session_date` | Market-session date | Human-reviewed case facts; `BenchmarkCase.session_date` |
| `cutoff` | UTC timestamp | Human-reviewed eligibility boundary; `BenchmarkCase.cutoff_ts` |
| `question` | Exact user wording, without answer hints | Frozen case source; neutral-query precedent in `post_import/case_pack.py` |
| `oracle_status` | `SUFFICIENT` \| `PARTIAL` \| `ABSTAIN` | Human adjudication; `INSUFFICIENT` is read-only legacy input |
| `acceptable_cause_labels[]` | `{cause_type, label, direction, materiality}` records; `cause_type` is one of `COMPANY_SPECIFIC_CATALYST`, `CONTINUATION`, `SECTOR_MOVE`, `MACRO_EVENT`, `FUNDAMENTAL_REPRICING`, `REPORTING_OR_ANALYST_CONTINUATION` | Human causal adjudication |
| `evidence_judgments[]` | Labels keyed by canonical evidence/chunk ID: role, support, materiality, temporal eligibility, independence group | Human review over the identity-bound pool |
| `expected_primary_evidence[]` | Canonical evidence/group IDs required when primary evidence exists | Human evidence review |
| `expected_refusal_reason?` | Frozen reason code, required for `ABSTAIN` cases | Human adjudication |
| `expected_attribution_type` | `EVIDENCE_BACKED_CAUSAL` \| `NO_MATERIAL_PUBLIC_CATALYST` | Human causal adjudication |
| `expected_research_behavior` | `{acceptable_initial_tasks[], expected_gap_reason_codes[], acceptable_corrective_actions[], corrective_recoverable, corrective_required}` | Human trajectory-policy adjudication |
| `notes` | Human annotation/adjudication note | Human reviewer |
| `dataset_version` | Semver envelope field | `packages/eval/catalyst_eval/benchmark/versioning.py` |
| `lineage` | Source, model-assisted fields, human-confirmed fields, UTC timestamps, adjudication state | `packages/eval/catalyst_eval/benchmark/lineage.py:LineageRecord` |

### Evidence judgment shape
- `packages/eval/catalyst_eval/benchmark/judgment.py:EvidenceJudgment` currently supports only chunk ID, grade 0/1/2, rationale, annotator, and timestamp.
- The V1.1 judgment must distinguish at least `primary_support`, `secondary_support`, `contradiction`, `lead_only`, `irrelevant`, and `ineligible`, because retrieval hit quality and attribution citation quality use different roles.
- The V1.1 judgment must retain canonical asset identity and evidence group identity in addition to chunk identity, because `packages/data-core` deduplication and independence policy operate above individual chunks.
- The V1.1 judgment must record materiality and temporal eligibility separately, because `metadata_only`, post-cutoff, and material evidence are different failure classes in the Frozen design.
- `AttributionType` is exactly `EVIDENCE_BACKED_CAUSAL` or `NO_MATERIAL_PUBLIC_CATALYST`; it is not a cause taxonomy.
- `CauseType` is exactly `COMPANY_SPECIFIC_CATALYST`, `CONTINUATION`, `SECTOR_MOVE`, `MACRO_EVENT`, `FUNDAMENTAL_REPRICING`, or `REPORTING_OR_ANALYST_CONTINUATION`.
- `MARKET_STRUCTURE_UNSUPPORTED` is a gap/capability reason in `expected_research_behavior.expected_gap_reason_codes[]`, never a `CauseType` or `AttributionType`.
- Human rationale remains required for non-obvious labels; `EvidenceJudgment`’s one-line/500-character constraint is a usable current invariant but must be extended only if the new annotation UI requires structured rationale fields.

### Dataset provenance
- The final GoldenCase artifact must be immutable by content hash and accompanied by a dataset manifest containing case count, split counts, source artifact IDs, annotation timestamps, reviewer identity, schema version, and lineage hash.
- The production runtime must never import or receive the GoldenCase file; the evaluator joins a run result to a case after execution by an opaque eval-run binding.
- A case’s retrieval pool must be generated and frozen under a `PoolManifest`/`EvalManifest`, not hand-selected from model output.
- The benchmark must preserve the original source/case IDs of T4 and earlier suites through an explicit `parent_case_id`/legacy reference rather than overwriting historical files.

## 7 Human Annotation Workflow

### Annotation authority
- Human annotation is the primary truth source under `docs/plans/2026-08-16-catalyst-vnext-frozen-v1-design.md`; `packages/eval/catalyst_eval/metrics/cause_match.py` and `citation_faithfulness.py` therefore cannot be promoted as primary truth merely because their LLM judge scores are stable.
- The annotator reviews the market event, the cutoff-bounded evidence pool, canonical source identities, and source relationships; the annotator does not see model output while creating the initial gold labels.
- Model-assisted suggestions may populate candidate labels only when `packages/eval/catalyst_eval/benchmark/lineage.py:LineageRecord.model_assisted_fields` records them and a human confirms or rejects each field.

### Practical workflow
1. Freeze the 12 Stage-1 case IDs, dataset version, and stratification manifest before any model result is opened.
2. Generate one identity-bound pool per case using the pinned data runtime and all four retrieval arms; store the pool through `PoolManifest` and exact source/chunk IDs.
3. Review the case facts, session date, cutoff, query, price move, and answerability without model-generated causes.
4. Label acceptable causes, causal type, status, primary evidence, secondary evidence, contradictions, materiality, temporal eligibility, and independent evidence groups.
5. Label expected initial research tasks and gap reasons before seeing any agent trajectory.
6. Perform a second pass on all abstain, conflict, multi-gap, and low-confidence cases; `LineageRecord` requires second-pass timestamps when adjudication is resolved.
7. Lock the dataset content hash and publish the stage manifest only after all required fields pass schema validation.

### Minimal review policy for one annotator
- The repository has one apparent project owner/annotator field in existing datasets, so the workflow should not claim multi-annotator agreement unless a second reviewer actually participates; `packages/eval/catalyst_eval/benchmark/lineage.py` is the current evidence for this distinction.
- For Stage-1, one primary annotator plus a documented second pass on all hard cases is sufficient for development gating; unresolved ambiguity must be marked non-scorable or adjudicated rather than converted into a forced label.
- Stage-2 should repeat the second-pass policy on stratified validation cases and record changes as a new dataset version rather than mutating Stage-1.
- Stage-3 must remain untouched by model outputs and development decisions until the holdout run is sealed.

## 8 Stage-1 Development Set

### Twelve-case design
- Frozen V1.1 requires 12 manually reviewed cases; the current `pre_b6_attribution_cases_v1.jsonl` has 12 rows but lacks the required GoldenCase fields and therefore cannot be adopted without reannotation.
- The Stage-1 set should preserve the existing useful coverage categories from `v1_2_p0_set.jsonl`, `v1_3_answerable.jsonl`, `v1_3_unanswerable.jsonl`, and `h_refusal_cases.validated.json`, but new case membership and labels must be frozen in a new V1.1 dataset version.
- The 12 cases should include sufficient, partial, and abstain outcomes; positive and negative moves; company-specific and macro/sector causes; direct primary reporting and no-material-evidence cases; and at least one recoverable corrective case and one multi-gap recoverable case.
- The Stage-1 stratification record, rather than an informal README statement, must bind the category counts and case IDs; `packages/eval/golden_set/README.md` currently documents distributions for older sets only.

### Stage-1 use
- Stage-1 is for schema validation, leakage checks, retrieval/attribution/trajectory development, and identifying one useful corrective signal; it is not a public accuracy claim.
- Stage-1 can be used to reject obviously invalid pipeline behavior and enforce hard integrity gates, but it must not be used to tune a large model-selection search and then reported as independent quality.
- T4’s ten-case identity and smoke artifacts remain a separate baseline; Stage-1 does not replace `T4_EXPECTED_CASE_COUNT` or the `FOUR_ARM_E2E_OK` contract.

## 9 Stage-2 / Stage-3 Design

### Stage-2
- Frozen V1.1 defines Stage-2 as approximately 40–60 stratified human-reviewed cases.
- Stage-2 should expand categories and source conditions while preserving the same GoldenCase and EvalManifest schema; changing schema requires a new dataset version and a new baseline comparison.
- Stage-2 is the minimum denominator for deciding whether A3 corrective research is useful and whether A4 bounded parallel research is neutral, useful, or harmful.
- Stage-2 can guide implementation and policy promotion, but any model or policy choice made after observing Stage-2 must remain ineligible for Stage-3 claims without a fresh holdout run.

### Stage-3
- Frozen V1.1 defines Stage-3 as 15–20 untouched holdout cases.
- Stage-3 cases must be selected and labelled before the final candidate configuration is sealed, with the case contents and pool manifests protected from development runs.
- Stage-3 execution must record a complete `EvalManifest`, runtime identity, code revision, model/prompt revisions, arm configuration, and metric specification.
- External quality claims require Stage-3, while T4 identity/smoke claims remain tied to their own approved evidence artifacts.

## 11 Retrieval Metrics

All retrieval metrics use human `GoldenCase.evidence_judgments` and the identity-bound `PoolManifest` as ground truth. Every result publishes numerator, denominator, excluded/non-scorable count, and `EvalManifest` ID.

| Metric | Numerator / denominator | Authority / source |
|---|---|---|
| Recall@K | Cases with at least one acceptable hit in top K / cases with at least one judged acceptable unit | Human evidence roles; automatic rank calculation; no LLM authority |
| MRR | Reciprocal rank of first acceptable hit, averaged / eligible cases | Human acceptable-role labels; automatic rank calculation |
| nDCG@K | Ranked graded gain / ideal gain for the same case | Human relevance/role judgments; automatic gain calculation |
| Primary-source hit | Cases with expected primary unit hit / cases with expected primary unit | Human `expected_primary_evidence[]`; automatic hit calculation |
| Duplicate-adjusted Precision@K | Unique acceptable canonical units / unique returned canonical units | Human judgments plus data-core IDs; automatic dedup count |
| Independent-evidence recall | Required independent groups hit / required independent groups | Human pinned relation; automatic group-hit calculation |
| Source diversity | Unique eligible source classes/groups per case; report distribution and minimum-coverage rate | Human eligibility plus data-core `source_class`; automatic count |
| Reranker contribution | Paired relevant/primary/precision change, reranked versus hybrid, over the same pool | Human judgments; automatic paired comparison |
| Temporal/ticker violations | Violating units / returned units, plus violating cases / eligible cases | Automatic cutoff/session/ticker checks against human case facts |
| Latency/degradation | Median/p95 and timeout/degraded counts / attempted retrievals | Automatic runtime trace/status; no human or LLM authority |

**Independent-evidence distinction:**

| Evaluation | Denominator / numerator | Authority |
|---|---|---|
| A. Retrieval over a pinned relation | Required human-reviewed independent groups hit / required groups in eligible cases; the relation is pinned in the case pool | Human-reviewed `GoldenCase` relation plus canonical data lineage; runtime grouping is only the submitted result |
| B. Independence/dedup algorithm itself | Correct predicted pair/group relations / all reviewed pair/group relations, with precision and recall reported separately | Separate human-labelled relation fixture; never runtime-generated grouping used as its own oracle |

The A metric evaluates retrieval against a fixed relation. The B metric evaluates the relation-producing algorithm against an independently labelled relation set.

## 19 Leakage Prevention

- `packages/eval/scripts/run_frozen_eval.py:FrozenDirectLLM`, `FrozenGraphLLM`, `_extract_case`, and fixture-derived golden causes demonstrate leakage patterns that are valid for deterministic tests but invalid for production quality evaluation.
- Production prompts and `ContextPack` must not receive GoldenCase expected status, cause labels, evidence judgments, gold IDs, or research-behavior fields; the evaluator joins those after the run.
- `case_id` may exist in evaluator metadata and `EvalManifest`, but it must not be used by production code as a lookup key for answers, causes, refusal labels, or evidence selection.
- Retrieval must use the same query, ticker, session date, cutoff, and data runtime policy as a real request; neutral query handling in `packages/eval/catalyst_eval/post_import/case_pack.py` is the relevant anti-hint precedent.
- Gold evidence must not be injected into the runtime database, FTS query, LanceDB table, provider prompt, or agent state; gold files must remain evaluator-only inputs.
- T4 fixed IDs in `packages/eval/catalyst_eval/post_import/t4_evidence.py` and user-smoke IDs in `user_smoke.py` are allowed as eval/smoke selectors only and must not enter production routing.
- Judge cache entries from `packages/eval/catalyst_eval/metrics/judge_base.py` must be keyed by complete `EvalManifest` identity and stored as diagnostic artifacts, not treated as primary truth.
- Leakage tests must scan prompts, serialized state, trace artifacts, and evaluator/runtime process boundaries for gold labels, secret values, and case-specific answer text.

## 23 Migration Regression Strategy

- Before semantic cutover, run the preserved legacy harness on the frozen baseline and record its report header, DB hash, LanceDB hash, code SHA, model IDs, and case distribution through `packages/eval/catalyst_eval/harness/frozen_eval.py`.
- Build the V1.1 evaluator around fixtures first, then run identical request facts through the new graph with gold hidden from runtime.
- Compare legacy and V1.1 outputs through an adapter, not by forcing the new graph to emit the old `GoldenEvent`/`AttributionResult` shape.
- Gate migration on identity and integrity parity before quality deltas: ticker/cutoff violations, citation resolution, runtime identity, secret leakage, ContextPack identity, and claim lineage must be zero/100% as specified by the Frozen design.
- Run the four retrieval arms with one candidate generation seam and paired inputs; do not compare separate hidden runtimes.
- Run A1–A5 one at a time with one changed policy variable, a predeclared eligible denominator, and an immutable `EvalManifest`.
- Keep T4 and user-smoke as regression smoke suites after cutover, but do not treat passing smoke gates as evidence that attribution quality improved.
- Any regression in refusal semantics, status normalization, or technical-failure classification must be reported separately from quality metric movement.

1. Seal the existing baseline and its identity before changing semantic behavior.

3. Repair canonical data and publish versioned derived corpus/index generations without changing the active pointer.
4. Build ObservationBuilder/MoveProfile, ResearchPolicy, EvidenceState, CoverageSummary, and ContextPack against fixtures, then bind them to the accepted generation.
5. Replace MCJ semantic ownership with EvidenceAnalyst, assessment, bounded correction, ClaimPlan, ClaimValidator, assurance, and Writer.

8. Delete legacy semantic/runtime/data paths only after their named gates, then prepare Stage-2/3 rather than expanding architecture.

This ordering minimizes rework because data identity precedes quality interpretation, while fixture-based contracts allow safe parallel progress.

## 39 Negative Result Policy

| Result | Decision |
|---|---|
| A1 ContextPack provides no value | Keep deterministic identity, cutoff, and evidence-lineage invariants; remove or simplify only the optional packing feature if Stage-2+ shows no benefit without regressions. |

| A5 MoveProfile has insufficient production coverage | Preserve deterministic available/missing fields and abstention semantics; do not invent values or make MoveProfile a hard dependency beyond its supported inputs. |

Stage 1 remains a development signal. A3/A4 architecture conclusions require Stage 2+ and predeclared eligible denominators. Temporal eligibility, materiality, canonical identity, independence truth, and citation integrity are correctness invariants and cannot be removed by an ablation result. Any architecture change follows the Frozen evidence/amendment process; no amendment is implied by a negative result alone.
