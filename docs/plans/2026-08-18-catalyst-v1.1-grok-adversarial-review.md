## PART 1 — System being reviewed

Catalyst V1.1 is a **single-process, SQLite-backed, evidence-bounded financial event-attribution workbench**. A developer submits a ticker, an exchange session, and a question. The system retrieves only point-in-time-eligible local evidence, lets **one Evidence Analyst** compete at most three causal hypotheses, optionally runs **one typed corrective retrieval action**, then lets **one streaming Writer** express a **ValidatedClaimPlan**. It returns `SUFFICIENT`, `PARTIAL`, or `ABSTAIN`, orthogonal to `EVIDENCE_BACKED_CAUSAL` vs `NO_MATERIAL_PUBLIC_CATALYST`. System failures are not abstentions.

### MODEL / HARNESS / ENVIRONMENT

| Layer | What it is | What it is not |
|---|---|---|
| **MODEL** | One Evidence Analyst (structured `AnalystDecision`) and one streaming Writer. Same Analyst role may run a second time after correction. Technical retry is the same role, same input. | Not a planner, judge, validator-LLM, compressor, reranker-LLM, supervisor, or post-answer reviewer. |
| **HARNESS** | Deterministic admission, TemporalIdentity, hybrid retrieval, Observation/MoveProfile, InitialResearchPolicy, EvidenceState, CoverageSummary, ContextPackBuilder, AssessmentNormalizer, CorrectiveResearchBatch, ClaimPlan/ClaimValidator, StructuralAssurance, RunManifest, SSE, Workbench reducer. | Not allowed to invent causes, raise status, rewrite answers, or treat serving status as materiality. |
| **ENVIRONMENT** | Local FastAPI process, WAL SQLite, LanceDB as dense serving only, exchange calendar, promoted snapshot/corpus/indexes, loopback Workbench, offline eval. | Not Redis/Kafka/Celery/Temporal, not web search, not multi-tenant SaaS, not distributed workers. |

### Final runtime spine (~20 lines)

```text
RunRequest + TemporalIdentity
→ identity-bound hybrid retrieval + structured PIT lookup
→ ObservationBuilder / MoveProfile
→ ≤3 Initial ResearchTasks (bounded parallel)
→ immutable EvidenceState
→ CoverageSummary (availability only)
→ ContextPackBuilder → persisted pack + rendered messages
→ Evidence Analyst (LLM #1)
→ AssessmentNormalizer (ceiling, gaps, optional 1-action batch)
    → optional CorrectiveResearchBatch
    → cumulative EvidenceState + rebuilt pack
    → Evidence Analyst round 2 (LLM #2)
→ ClaimPlan → ClaimValidator → ValidatedClaimPlan
→ Streaming Writer (LLM #2 or #3)
→ StructuralAssurance (no rewrite)
→ SQLite events/artifacts → SSE replay/live tail → Workbench
→ GoldenCase / EvalManifest offline
```

Logical model calls: **2** normal, **3** with one corrective round.

### Opposite error — model doing code’s job

The design forbids this and treats violations as `MODEL_SCHEMA_FAILURE`:

- ticker / cutoff / TemporalIdentity
- runtime IDs, recoverability, capability, budgets, deadlines
- independence-group assignment
- status ceiling
- executable CorrectiveResearchBatch
- execution admission / lifecycle

Raw `AnalystDecision` cannot contain those fields (`extra=forbid`). Query hints are stripped of tickers, dates, URLs, SQL, source selectors. **This side of the boundary is specified well.**

The live repo still violates it: Critic owns sufficiency/action, Judge owns causes+prose, Validator may LLM-repair. That is a migration fact, not a V1.1 design endorsement. M5 must delete those paths, not wrap them.

| Scenario | Handled? | Severity if not |

| **A. ## PART 9 — SSE replay / live-tail

**Intended protocol is correct:** SQLite is source of truth; condition is wakeup only; at-least-once; client dedup `(run_id, seq)`; cross-run Last-Event-ID rejected; restart replays from disk; heartbeat is a non-sequenced comment; disconnect does not cancel.

### Attacks

| Attack | Outcome |
|---|---|
| Lost wakeup (commit between query and wait) | Prevented if reader holds the condition lock until `wait()`. Writer cannot notify without that lock. |
| Duplicate event | Allowed; reducer ignores applied seq. |
| Missed event after first batch | **Phase 7 §18 as written can miss live events** if implemented as a single query. Phase 5’s `while` loop re-queries after framing. During framing the lock is released, so notify can fire with no waiter. Recovery = next query, not the notify. |
| Cross-run cursor | 400. |
| Process restart | Condition dies; first query replays. |
| Reconnect after terminal | Replay through terminal, close. |
| Heartbeat race | Timeout re-queries. Masks lost notify by up to 10 s. |
| Commit between query and wait | Blocked by lock protocol. |
| Stale Last-Event-ID | Replay `seq > cursor`. At-least-once. |

### Exact bad timeline if Phase 7 is implemented literally (no loop)

```text
t0  Client connects, cursor=0, query → events 1..5 (RUNNING)
t1  Implementation frames 1..5 and **returns** (no while)
t2  Writer commits 6..N, notify (no waiter)
t3  Client hangs until TCP idle / never sees answer.delta
```

If instead it waits after framing **without** re-querying:

```text
t0  Query → 1..5; release lock; frame 1..5 (slow)
t1  Writer commits 6, notify (no waiter)
t2  Client waits 10 s heartbeat, then re-query → 6
```

Events are not lost forever, but first-token latency becomes heartbeat-bound. Frozen wants p95 first token < 20 s *and* perceptible streaming. A 10 s hole after every batch is a contract miss.

**Verdict:** persisted replay + condition + at-least-once + `(run_id, seq)` dedup **is** the right design. Phase 7’s write-up is one missing `while` + “re-query before wait” away from being implementable without invention.

## PART 10 — Writer stream / assurance

```text
provider delta → adapter → coalescer (50 ms or 2,048 UTF-8 chars)
→ persisted answer.delta (ordinal + cumulative counts)
→ SSE → reducer
→ Answer = concat(deltas) at answer.completed
→ StructuralAssurance
```

| Attack | Handled? |
|---|---|
| Text reconstruction | Yes: hash(concat(accepted deltas)) must equal Answer; mismatch = `STREAM_PERSISTENCE_FAILURE`. |
| Ordering | `delta_ordinal` + seq. |
| Unicode / UTF-8 | Concatenation is safe if splits are at Unicode **code-point** boundaries. “UTF-8 characters” is slightly sloppy; byte-splitting would corrupt. **WRITER-01.** |
| Retry after partial output | Forbidden after first accepted delta. One same-input retry before that. |
| DB failure after some deltas | Fail closed; invalidate provisional. Buffer then `STREAM_PERSISTENCE_BACKPRESSURE`. |
| Browser disconnect | No cancel; reconnect replays deltas. |
| Cancellation | Stop accepting deltas; discard late provider output; invalidate if any delta persisted. |
| Provider timeout | Same as post-delta failure. |
| Assurance failure after provisional | `assurance.completed(valid=false)` + `run.failed(ASSURANCE_FAILED)` + `provisional_output_invalidated=true`. No rewrite, no second Writer. |

**Can the system honestly say “what the user saw is exactly the persisted provisional output”?**

**Yes**, if the reducer appends only persisted `answer.delta` text and never interpolates provider tokens locally. After failed assurance the UI must replace that text with an invalidated state, not keep it as the result. Phase 5 §17 and Phase 7 §21 require that.

Answer bytes must be frozen at `answer.completed`. The later terminal txn may attach assurance metadata; it must not mutate text.

## PART 15 — Findings

### SSE-01

- **SEVERITY:** HIGH
- **CATEGORY:** Runtime / SSE
- **LOCATION:** Phase 7 §18; Phase 5 §14 (correct while-loop); repo: no `/stream` yet
- **FAILURE SCENARIO:** Reader queries events 1–5, frames them, and (per Phase 7’s numbered steps) does not loop. Writer commits `answer.delta` 6..N and notifies a dead waiter. Client never streams the answer, or waits a 10 s heartbeat per batch.
- **WHY IT MATTERS:** Frozen requires persisted live tail and first-token latency targets.
- **DOES PHASE 7 ALREADY HANDLE IT?** PARTIALLY (lock protocol and heartbeat; loop omitted)
- **MINIMAL FIX:** Copy Phase 5’s `while streaming` into Phase 7 §18; after any non-terminal batch, re-query before `wait()`. Use `notify_all()`.
- **IMPLEMENTATION BLOCKER?** YES for unsupervised M6 planning; NO for architecture.

### CLAIM-01

- **SEVERITY:** HIGH
- **CATEGORY:** Deterministic/semantic boundary
- **LOCATION:** Phase 7 §13; Phase 4 §26; Frozen §6.5 (no direction check); ClaimPlan fields in Frozen §6.5 / Phase 4 §23
- **FAILURE SCENARIO:** Implementer either (a) NLP-parses claim `statement` for UP/DOWN, or (b) silently drops a named safety check, or (c) invents a field mid-implementation.
- **WHY IT MATTERS:** This is exactly the boundary Frozen exists to keep clean.
- **DOES PHASE 7 ALREADY HANDLE IT?** NO
- **MINIMAL FIX:** Add optional structured `asserted_direction: UP|DOWN|FLAT|UNKNOWN` and `time_scope` on ClaimPlan, copied from Analyst/MoveProfile — **or** strike the check.
- **IMPLEMENTATION BLOCKER?** YES for M2 schema planning; NO for Frozen.

### DATA-01

- **SEVERITY:** HIGH
- **CATEGORY:** Data / release gate
- **LOCATION:** Frozen §10 “benchmark-relevant SEC parse success ≥ 90%”; Phase 2 §9 (100% `section_parse_degraded`, 1,659/5,229 documents); Phase 7 §5.3 / §29 / M3 exit
- **FAILURE SCENARIO:** M3 treats the gate as section-boundary quality and never exits (0% today), **or** silently redefines “parse success” after seeing results.
- **WHY IT MATTERS:** After-close eligibility and section-scoped citations depend on what “success” means.
- **DOES PHASE 7 ALREADY HANDLE IT?** PARTIALLY (fail-closed accepted-time; reparse+rebuild; gate metric unspecified)
- **MINIMAL FIX:** Pin the metric as successful primary-document extract + accepted-time-or-fail-closed `eligible_at` on benchmark-relevant accessions. Keep section-degradation as a quality flag, not the 90% gate, unless a Frozen amendment says otherwise.
- **IMPLEMENTATION BLOCKER?** YES for M3 exit; NO for M1.

### DATA-02

- **SEVERITY:** HIGH
- **CATEGORY:** Data quality limitation (not architecture)
- **LOCATION:** Phase 1/2 promoted snapshot; 21 active vs 30,945 metadata-only reported-news chunks; Phase 7 §10 / §29
- **FAILURE SCENARIO:** Stage-1 company-news cases retrieve only titles; Analyst cannot support causal claims; system correctly PARTIAL/ABSTAIN; someone reports this as “Analyst failure.”
- **WHY IT MATTERS:** Attribution quality and A3 usefulness are data-bound. Design already refuses metadata-only bodies.
- **DOES PHASE 7 ALREADY HANDLE IT?** YES (selective reimport + content-state gate + honest abstain)
- **MINIMAL FIX:** None architectural. M3 must actually recover bodies for the Stage-1/2 window or those cases are labeled coverage-limited, not model-limited.
- **IMPLEMENTATION BLOCKER?** NO for design; YES for credible M7 news-attribution numbers.

- **FAILURE SCENARIO:** Workbench and tests bind Frozen names; app emits Phase 7 names; replay/dedup and contract tests fork.
- **WHY IT MATTERS:** Phase 7 asserted 0 Frozen amendments and unchanged SSE semantics.
- **DOES PHASE 7 ALREADY HANDLE IT?** NO

## PART 16 — Final verdict

### 1. BLOCKERS

**None.** Nothing in this design is unimplementable against the repository, and nothing requires multi-agent, ReAct, GraphRAG, Redis, Kafka, Temporal, WebSockets, or a second corrective round for Frozen V1.1 to meet its own contract.

### 2. HIGH-SEVERITY FINDINGS

- **SSE-01** — Phase 7 live-tail loop omitted
- **CLAIM-01** — ClaimValidator direction/time has no field
- **DATA-01** — SEC “parse success ≥ 90%” metric ambiguous vs 0% section parse / 32% document coverage
- **DATA-02** — Reported-news full text nearly absent (quality limitation; design refuses safely)
- **API-01** — Public SSE field names diverge from Frozen
- **AGENT-01** — `ABSTAIN + EVIDENCE_BACKED_CAUSAL` can be verbalized as a cause

### 3. MEDIUM / LOW FINDINGS

**Medium:** SQLITE-01 unique admission indexes; RUNTIME-01 capacity wording (Phase 5 total = 6 vs Frozen 2–4); TIME-01 60 s vs 3 LLM calls; WRITER-01 code-point splits; OPS-01 which identities M1 seals.

**Low:** SSE-02 `notify_all`; CORR-01 zero-novelty vs round 2 wording; ISSUER-01 thin issuer registry.

### 4. Design areas that survived adversarial review

- Model / harness / environment split and the 2/3-call budget
- Orthogonal status / type / cause / research-decision / lifecycle ontologies
- Materiality vs serving status; source class vs evidence role vs independence
- Fail-closed unknown lineage; no publisher authority score
- ContextPack as derived view; persist pack + rendered messages before dispatch
- AssessmentNormalizer: model may lower, never raise; no executable batch from the model
- One corrective action, structural novelty, capability registry, fingerprint stop
- ClaimPlan as maximum public surface; assurance does not rewrite
- SQLite `BEGIN IMMEDIATE` + `UNIQUE(run_id,seq)` + conditional lifecycle
- Hidden gold, predeclared A3/A4 denominators, Stage 1 cannot promote architecture
- Eight-milestone order; MCJ deleted at M5, not dual-run
- Honest thin structured context (UNKNOWN, not invented SPY/peers)
- Zero Frozen amendments required for the architecture to stand

### 5. EXECUTABILITY VERDICT

**Executable as an architecture.** Not quite executable as a *single* implementation spec: Phase 7 still needs a one-page errata (SSE loop, ClaimPlan direction, public envelope names, Writer abstention rule, SEC gate metric, admission-slot reading of capacity) before a low-cost planner should write M2/M5/M6 plans unsupervised.

### 6. REQUIREMENTS-SATISFACTION VERDICT

The harness, if implemented and if named data repairs land, **does** satisfy Frozen V1.1’s product/engineering goals. PIT safety and honest `NO_MATERIAL` are **data-gated**. Citation safety is **structurally** satisfied and **semantically** only eval-bounded — which is what Frozen promised. Eval credibility is **program-satisfied**, not Stage-1-satisfied.
